# プロフィールとフレンド

## 画面と導線

- `/game/profile/`: 自分の名前（12文字）、カードのアイコン、ひとこと（80文字）を保存。初期コメントは「よろしくお願いします！」。Googleの写真やメールアドレスは公開プロフィールに含めない。
- `/game/profile/?id=...`: 他の人の公開プロフィールとフレンド申請。プロフィールのリンクをコピーして共有できる。左上のボタンでソーシャルへ戻る。フレンドがいまいるルームをワールドのカードのように表示し、選ぶと参加（募集中）・観戦（対戦中）できる。
- プロフィールでは、保存済みのデッキから3つまで選んで掲載できる。デッキ自体は共有URLで単体取得できるが、保存済みデッキの一覧を取得できるのは所有者だけ。プロフィールにはIDだけを保存する。プロフィールに掲載していないデッキでも、共有URLを知っていれば単体取得できる。
- `/game/social/`: VRChatの「フレンドの現在地」のように、フレンドを募集中のルームごとにまとめて並べる。ルームのカードから参加・観戦でき、フレンド解除もここで行う。ログインして観戦しているフレンドも、そのルームに並ぶ。どのルームにもいないフレンドは見出しを付けずに一覧にする。
- `/game/notifications/`: 通知。届いた申請の承認・見送り、送った申請の取消、プロフィールのリンクからのフレンド追加。
- ルームのホストが「フレンドに対戦を募集する」を押すと公開。空席なら「参加」、観戦可能な対戦中なら「観戦」へ入る。プロフィールのUIDとサーバーが認証したホストUIDが一致し、実際に接続している場合だけ募集として扱う。
- ルームIDを知っている人が参加できる既存ルールはそのまま。募集先の一覧を見られるのは承認済みフレンドだけ。

## Firebaseの保存対象

`profiles/{uid}`: displayName, iconCardId, comment, decks（公開するデッキのID、3つまで）, createdAt, updatedAt。単体の公開読み取り、所有者の書き込みだけ許可。プロフィール一覧の全件取得は許可しない。

`friendships/{sortedUidA~sortedUidB}`: members, requestedBy, status, createdAt, acceptedAt。申請側はpendingだけ作成でき、承認は相手側だけ。メンバーの差し替えや他人のフレンド一覧の読み取りは禁止。双方どちらからでも削除でき、削除後は相手の募集を読めない。

`recruitments/{uid}`: roomId, updatedAt。所有者が明示的に公開/取り下げする。承認済みフレンドだけ読み取り可能。古い募集が残っても、実ルームとホストの接続をRedisで確認して表示するため、解散したルームへ誘導しない。

`watching/{uid}`: roomId, updatedAt。ログイン中に観戦画面で対戦を見ている間だけ書き、1分ごとに更新、離れると削除する。読み取りは承認済みフレンドだけ。3分以上更新がないもの、観戦できる対戦中でなくなったルームは表示しない。観戦者はサーバー上では人数だけで、誰が見ているかはサーバーに渡さない。

常時のオンライン通知はFirebaseに書かない（観戦中の更新は観戦画面を開いている間だけ）。ソーシャル画面を開いている間だけ必要なドキュメントを購読する。ルーム状態は既存サーバーを15秒おきに確認し、非表示タブでは確認を止める。初期実装のフレンド・申請一覧は合計100件まで。大量利用向けの検索・ページ分けは別途追加する。

外部の有料DBやCloud Functionsは追加しない。ただしFirestoreは既存プロジェクトの無料枠と料金プランに従う。無制限の無料利用を保証する仕組みではない。

## 観戦とリプレイ

フリー対戦の一覧は名前、プレイアブルのアイコン、観戦人数と公開プロフィールへのリンクを表示する。進行中は両者の未公開の手札と山札の並びを伏せる。形勢は公開盤面だけで計算した目安。伏せ札の内容は計算に使わず、デッキから先読みする不明カードには共通の固定値を使う。

旧Podの観戦処理が手札を公開してしまわないよう、生存中の全Podが新しい手札非公開方式に対応するまで、新規フリーマッチの公開観戦を有効にしない。混在中に始めた非公開対戦を後から勝手に公開しない。

公開観戦ありで開始したフリー対戦は、終了後に完全な記録・両デッキを観戦者も読める。旧来の非公開対戦と通常のルームの履歴は参加者だけに限定する。再生はCPU戦の後のリプレイと同じ対戦画面で行う。記録した各局面を観戦と同じ流れで順に盤面へ送り、演出付きで見せる（ルールは実行しない）。左上の「やめる」かメニューで中断でき、終わるとリザルト画面から最初から再生し直せる。場面指定URL（`step`）はその手から再生する。観戦者に「自分のデッキ」と誤表示しない。

## 認証と公開

公開用の名前は保存したプロフィールから取得し、Googleアカウントの名前・メール・写真へフォールバックしない。プロフィール取得中は安全な仮名を表示し、ルーム作成・参加・フリーマッチ開始は読み込み完了を待つ。初回プロフィールにもGoogle名を自動入力しない。CPU対戦の勝敗表示も同じ公開プロフィールを使う。

ログイン中の対戦名はプロフィール名に固定し、変更はプロフィール画面から行う。ゲスト名だけは入力・専用保存を許可し、旧来のアカウント共通の名前キャッシュは読み込まない。共有デッキには現在のプロフィール名を作成者として表示する。対戦一覧、ルーム、履歴・公開リプレイは認証済みのプロフィールUIDから現在の名前を解決し、取得失敗・未作成の場合は「プレイヤー」とする（保存された旧名には戻さない）。サーバーの公開名キャッシュは最大60秒、最大2000件、取得の同時実行は8件。コマンドの送受信・演出はプロフィール取得を待たない。過去の記録は保存時のハッシュを検証した後、配信用コピーの名前とログ先頭のプレイヤー名を解決する。原本・カード名・デッキ名・対戦局面は変更しない。配信の `publicNamesResolved: true` はハッシュが原本に対応することを示す。古い記録にプロフィールUIDがなければ関連付けはできない。

プロフィールURLなどに含むFirebase UIDは公開用の識別子であり、メールアドレスやログイン用の秘密ではない。ゲームサーバーには認証のためID tokenを送るが、対戦相手・観戦者への応答にtokenやGoogleプロフィールを含めない。ログイン中はサーバーでも提出された別名を使わず、認証済みUIDの公開プロフィール名を採用する。ゲストは名前欄の値を使う。フルーツ・プレイアブル・盤面などの対戦情報も公開範囲に含まれる。

ユーザーが変わるとプロフィール編集・ソーシャル画面・取得済みのフレンド情報を破棄する。Firebase ID tokenとFirestoreルールで所有者を確認し、ゲームサーバーに送るプロフィールUIDは認証済みのUIDからだけ設定する。

Firestoreルールは `firebase.json` から `firebase deploy --only firestore:rules --project pplale-6cca0` で公開する。管理者のCLIログインが必要。既存のデッキ共有ルールを維持したうえで新しいコレクションだけ追加する。

## ローカル検証

```
pnpm dlx firebase-tools@15.34.0 emulators:start --only firestore,auth --project demo-pplale-social
PPLALE_FIREBASE_RULES_TEST=1 node --test tests/social-rules.test.mjs
```

ブラウザの統合テストは `NEXT_PUBLIC_FIREBASE_EMULATORS=true` で起動した分離プレビューを利用する。認証とFirestoreの接続先はローカルに固定し、プロジェクトを `demo-pplale-social` に切り替える。本番環境ではこの変数を設定しない。
