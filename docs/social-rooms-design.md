# 集まって遊べるルームと共通メニューの設計

更新日: 2026-10-24

本書は、ルームをフレンドと集まれる場所にするための設計。13章の計画に沿って実装を進めている。現在の動作は [プロフィールとフレンド](social.md)、[ルームサーバー](../services/room-server/README.md) を参照する。

## 1. 今回決まったこと

- **ゲームを普通に起動したら、最初に通常ルームの盤面へ入る。** 有効な在室セッションがあればその部屋へ復帰し、なければ新しいルームを作る。起動時のルームも共有URLから入るルームも、同じ入室・所有権・寿命の仕組みを使う。
- 新しく作る部屋の種類（公開範囲）は設定であらかじめ選び、保存できる。**初期値はインバイト。** 起動時に新規作成するルームにもこの設定を使う。
- インスタンスの公開範囲など、部屋自体の設定は作成時に決め、存続中は変更できない。
- ルームには作成時に名前を付けられる。
- 部屋を作った人は作成者として固定する。オーナーが交代しても作成者は変わらず、ソーシャルのルーム詳細にも元の作成者を表示する。
- 作成者・最初の入室者も、対戦席に座らず観戦や待機ができる。
- ルームオーナーはルールを変更できる。
- 公開範囲はパブリック、フレンド、フレンド＋、インバイト、インバイト＋の5種類。
- 対戦者が抜けても、ほかに入室者がいればルームは残る。観戦者・待機者も入室者に含む。
- **無人になったら、ほぼすぐルームを閉じる。** 無人のルームを長時間保存しておく方式にはしない。
- 一時的なタイムアウトなどで無人になり、元のルームが閉じた場合は、新しいルームを作り、ロードを挟んで入り直す体験にする。
- **オーナーがいなくなったら、オーナー不在になる。** 自動で次の人を選ばず、部屋にいる誰でもオーナーになれる。
- 観戦・待機中でも、盤面上の空席から対戦に参加できる。試合後は席を維持して次の対戦を待つか、席を空けて観戦に移るか選べる。
- 起動時に入ったルームを含め、どのルームでもCPUを呼び、同じ盤面のまま対戦できる。
- `/game/` からの起動と招待URLからの直接起動は、ぷぷりえーるのロゴを見せる全画面の起動ロードを挟む。ランダムなカードと短い紹介を表示し、ロードバーは使わない。ルーム間の移動は軽い接続表示にする。
- ゲーム内のどこにいても共通メニューを開ける。起動時に入ったルーム・ほかの人のルーム・対戦中・観戦中も、Escキーまたはメニューボタンでランチパッドのように開閉する。
- ルームの共有リンクをDiscordなどに貼れる。OGP画像はルール別のルームサムネイルにする。
- 無人閉鎖後に新しいルームができても、前のルーム・招待のURLは失効する。ソーシャルから探せるのは公開範囲が許す新しいルームだけ。
- インバイト／インバイト＋のルームはソーシャルに表示しない。フレンドも直接入れず、招待URLを受け取るか、招待をリクエストして承認を待つ。
- インバイトはオーナーが招待URLを共有できる。URLを知る人は入れるが、相手を限定する設定も用意する。

以下の「案」「初期案」は、上記を実現するための実装提案。未確定項目は末尾にまとめる。VRChatの現行仕様そのものを再現することを目的にはしない。

## 2. ルーム・入室者・対戦席を分ける

ルームは人が集まる場所で、その中に1組の対戦席を置く。初期案では1ルームにつき同時に1対戦。複数卓や交代の予約列は別の拡張とする。

| 概念 | 持つもの・役割 |
| --- | --- |
| ルーム（インスタンス） | ID、作成時に固定する名前・公開範囲・作成者、次の対戦に使うルール、入室者、現在のオーナー、対戦席、対戦 |
| 入室者 | 入室者ID、認証済みアカウントまたはゲストの識別、接続状態、選択中のデッキ |
| 作成者 | 最初に部屋を作った人。部屋が続く間は変更しない。退出後も詳細の作成者欄に残る |
| オーナー | 現在の管理権限を持つ入室者。別の人へ移るか、不在になることがある |
| 対戦席 | 2席。各席は入室者ID、CPU、または空席 |
| 対戦 | 試合ID、開始時の2人・ルール・デッキ、盤面、持ち時間、結果 |

オーナーと対戦席は独立する。オーナーが観戦し、ほかの2人が対戦できる。対戦しない入室者は、対戦がなければ待機、対戦中なら観戦になる。

作成者とオーナーも独立する。作成者が退出して別の人がオーナーになっても、ルームの作成者IDと作成時の公開範囲・名前は変えない。無人でルームが閉じ、新しいルームを作ったときは別インスタンスなので、新たに作成した人がそのインスタンスの作成者になる。

同じ人の複数タブ・接続を別の席や別の入室者として数えない。ゲストを含めた具体的な識別方法は実装時に確定する。対戦席を持つ人の別タブには、観戦者向けの追加情報を送らない。

### 起動時に通常ルームへ入る

ゲーム起動時は、自分がいるルームの盤面を表示する。初期表示でメニュー全体を開くのではなく、盤面から必要な操作を呼び出す。有効な在室セッションがある場合はそのルームへ復帰し、ない場合にだけ新しく作る。

```text
ゲームを開く
  → 全画面の起動ロードを表示する
  → 有効な在室セッションがあれば復帰する
    なければ保存した部屋の種類を使って通常ルームを作成する（未設定はインバイト）
  → 盤面に自分が表示される
      ├ デッキを選ぶ・準備する
      ├ 空席にCPUを呼んで対戦する
      ├ メニューを開く → フレンド・招待・カード・設定など
      └ ほかの人を招く／別のルームへ遊びに行く
```

起動時に作られたルームは、URLで人を招いて対戦・観戦できる通常ルームそのもの。「ホーム」という種類や個人専用の場所は設けない。作成者が退出してもほかの入室者がいれば続き、無人になればほぼすぐ閉じる。起動した経路だけを理由に、入室条件・所有権・席・CPU・共有URLの動作を変えない。

初期案:

- 盤面上の自分はプロフィールのアイコン・名前などで表現する。立体的な移動空間や操作キャラクターを追加するかは、この計画の必須範囲には含めない。
- 盤面に自分がいることと、対戦席を占有することを分ける。自動着席は前提にせず、観戦を選べる設計を保つ。
- デッキは着席前にも選べる。選択内容は入室者の準備として持ち、着席時と準備完了時にその部屋のルールで検証する。
- 招待や共有リンクから来た場合は、目的のルームへの入室を優先し、その前に不要なルームを作らない。入室できなければ理由を示し、新しいルームを作る導線を出す。
- ほかの部屋へ移ったら元のルームから退出する。ほかの人が残っていれば、その部屋はオーナー不在で継続する。新しいルームを作る際に残った人を追い出したり、以前のオーナー権限を自動で取り戻したりしない。
- 作成・入室中はロードを表示し、確定してから盤面を操作できるようにする。失敗時は接続状態と再試行を示し、作成を無限に繰り返さない。

| 操作 | 接続中の表示 | 次に表示する場所 |
| --- | --- | --- |
| `/game/` から通常起動・再読み込み | 全画面の起動ロード | 有効な在室セッションがあればそのルームの盤面を復元する。なければ通常ルームを作成して表示する |
| 招待・共有URLから直接起動 | 全画面の起動ロード | 入室できたリンク先の盤面。先に別ルームを作らない |
| ルームAからルームBへ移動 | 軽い接続表示 | ルームBの盤面。ルームAから退出し、ほかの人が残る場合は存続する |
| 新しいルームを作る | 軽い接続表示 | 現在のルームを退出し、新しいIDの通常ルームを作成してその盤面へ移動する。以前の部屋へ自動で戻らない |

起動時やメニューから自動作成するルームには、設定した公開範囲と作成時の初期名を使う。初期名の具体的な文言と、複数端末でどこまで同じ在室セッションを復元するかは実装時に決める。

## 3. 公開範囲と入室判定

### 作成時の部屋の種類を保存する

設定に、新しく作る部屋の種類を選ぶ項目を置く。選択肢は下表の5種類で、保存値がなければインバイトを使う。起動時にルームを作る場合も、毎回作成ダイアログで選び直す必要はない。

この設定は次に自分が作成するルームに適用する。保存しただけでは、いま在室している部屋の公開範囲を変更しない。作成後はオーナーも公開範囲を変更できず、変えたい場合は新しいインスタンスを作る。他人のルームに入るときはその部屋の作成時の公開範囲を使う。無人閉鎖後に元の部屋を再作成する処理は、明示的な新規作成と区別し、後述の復旧方針に従う。

ルーム名と公開範囲は作成時に確定する「部屋の設定」とする。招待URLの発行・取消は公開範囲を変更する操作ではない。フルーツ、拡張プレイアブル、持ち時間などは対戦ごとの「試合ルール」で、オーナーが次の試合に向けて変更できる。これによって、部屋の公開範囲を固定する指定と、オーナーが対戦ルールを変えられる指定を両立する。

設定はゲームを開き直しても残す。ログイン時のアカウント保存・端末間同期と、ゲスト時の端末保存の分担は実装時に詰める。初期設定の取得に失敗した場合は、意図せずパブリックで作成せず、インバイトを使うか再試行できるようにする。

### 種類ごとの入室条件

| 公開範囲 | 入室できる人 | 招待を出せる人 |
| --- | --- | --- |
| パブリック | 誰でも | 共有リンクで案内できる |
| フレンド | 作成者の承認済みフレンドだけ（初期案） | ルームURLで案内できるが、フレンド条件は必要 |
| フレンド＋ | 作成者、または現在の入室者の承認済みフレンド（初期案） | ルームURLで案内できるが、フレンド条件は必要 |
| インバイト | オーナーから招待を受けた人。共有された招待URLを知る人も含む。限定URLを使えるのは指定相手だけ | 現在のオーナーだけ |
| インバイト＋ | 現在の入室者から招待を受けた人。共有された招待URLを知る人も含む。限定URLを使えるのは指定相手だけ | 現在の入室者全員 |

フレンド＋の起点には観戦者・待機者も含む。退出した人は、新規入室のフレンド判定の起点から外れる。

初期案:

- フレンド関係はログイン済みアカウントで判定する。ゲスト参加を認める公開範囲・招待方法は別途確定する。
- フレンド関係と招待はサーバーで確認する。画面でボタンを隠すだけではなく、HTTPとWebSocketの入室処理でも同じ条件を適用する。
- すでに在室している人は、起点のフレンドの退出やオーナー変更だけでは追い出さない。以後の新規入室に新しい条件を使う。
- 初期案ではフレンド判定を固定された作成者に結び付ける。オーナー不在中でも作成者のフレンドは入室できる。フレンド＋では現在の入室者のフレンドも入室できる。
- インバイトはオーナー不在中、新しい招待を発行できない。インバイト＋は在室者が発行できる。発行済み招待の有効性は、発行者の退出だけでは失わせず、期限・失効条件で判断する。
- パブリック・フレンド・フレンド＋のルームは、それぞれの公開範囲に応じてソーシャルに表示する。インバイト・インバイト＋の部屋は、フレンドの現在地やプロフィールを含め、ソーシャルのルーム一覧に表示しない。
- 共有ページに出す情報は公開範囲に合わせる。非公開ルームの存在・名前・在室者を、招待されていない人に公開しない。

インバイト／インバイト＋では、**招待する人がURLを渡せば、それ自体が招待**になる。受け取った人に別の承認操作を求めない。通常の招待URLは、知っている人なら入れる。相手を限定して作ったURLは、指定したログイン済みアカウントだけが使える。フレンドであっても招待URLや承認済みの招待を持たなければ入れない。フレンド型のルームURLを知るだけでは、フレンド条件を通過できない。

URLを受け取っていない人は「招待をリクエスト」できる。インバイトではオーナー、インバイト＋では在室者が許可できる。許可された人にだけ、そのルームの入室権を渡す。初期案では、フレンド一覧で相手にリクエストを送れるが、相手がいるルームの名前・ID・公開範囲は見せない。リクエストの送信・拒否・通知の具体的な画面は実装時に詰める。

実装案では、部屋のURLに推測できない招待用トークンを付ける。6桁の部屋IDだけを秘密として扱わない。オーナーまたはインバイト＋の発行者は、招待URLをコピーし、必要なら取り消せる。限定先を確認できないゲストは、限定URLで入れない。トークン自体を画面の説明文やOGP画像に含めない。旧ルームが閉じた時点で、そこに結び付くすべての招待URLも失効する。

## 4. オーナー不在と引き継ぎ

1. 作成時は作成者がオーナーになる。対戦席には自動で座らせない。
2. オーナーが明示的に退出するか、サーバーが接続切れによる不在を確定すると、オーナーを不在にする。
3. 残った入室者に「オーナーになる」を表示する。対戦者・観戦者・待機者の誰でも選べる。
4. サーバーは「現在オーナー不在」「申請者が在室中」を確認し、最初に成功した1人をオーナーにする。
5. 同時に複数人が押しても、オーナーは1人だけ。元のオーナーが戻っても、権限は自動で戻さない。

オーナー不在中は、次の試合のルール変更を止める。ルーム名・公開範囲は、オーナーの有無にかかわらず作成後に変更できない。対戦・観戦・通常の席への着席は続けられる。

オーナー変更後も、作成者・ルーム名・公開範囲は変えない。次の試合のルールも、引き継いだだけでは変わらない。フレンドルームの入室基準も作成者のフレンドで固定する案とし、オーナー変更だけで入室可能な人を切り替えない。

## 5. ルームの寿命と再接続

### 無人になったとき

在室人数は、サーバーが確認できる有効な入室者の数。対戦席の人数やソーシャル画面の表示人数では判断しない。

- 誰かがいれば、対戦の終了・席の空き・オーナー不在によってルームを閉じない。
- 最後の1人が退出し、在室人数が0になったら、ほぼすぐ閉じる。初期案は0〜数秒程度で、正確な秒数は未確定。
- 明示的な退出はその場で処理する。通信断は短い生存確認の期限が切れてから不在とする。「無人と判断するまでの時間」と「無人になってから閉じるまでの時間」を分ける。
- 別Podや別タブに有効な接続がある人を退出扱いにしない。サーバー1台が接続を見失ったことだけで無人としない。
- 作成APIの完了から最初の接続までには、短い入室待ち期限を設ける。これを無人ルームの長期保持には使わない。

現在の生存確認は15秒周期・3周期分の接続期限なので、そのままでは即座に通信断を検知できない。新しい体験に必要な検知時間は、通信量やスマートフォンの挙動と合わせて調整する。

閉鎖と新規入室はサーバーで競合を解決する。「0人と読んだ後に入った人がいるのに削除する」状態を作らない。画面上では閉鎖した時点で一覧から外し、以後の入室を拒否する。内部の閉鎖記録は、古い接続への通知や復旧判定のために短時間残してよい。

### 一時的に切れたとき

| 戻った時点の状態 | 動作 |
| --- | --- |
| 元のルームがあり、自分の在室・席を再認証できる | 同じルームに再接続する |
| 元のルームはあるが、自分の在室が失効している | 現在の入室条件で再入室する。オーナー権限は自動復元しない |
| 無人で元のルームが閉じている | ロード画面を挟み、新しいルームを作って入る |
| 別のルームへ移動済み、または自分で退出した | 古い接続処理で勝手にルームを作らない |

新規作成は元ルームの復活ではなく、別IDのルームへの移動として扱う。対戦途中の盤面・席・準備完了・オーナー権限・招待をそのまま復活させない。無人閉鎖による対戦の扱いは、通常の勝敗と区別して履歴に残す。

再作成の初期案:

- 直前の在室を証明できる再接続処理だけが対象。古い共有リンク・招待URLを開いただけの訪問者には、自動でルームを作らない。
- 新インスタンス作成時に、前の名前・ルール・公開範囲を初期値として使う案。ただし作成者は新しく作った人になり、作成後はそのインスタンスの名前・公開範囲を変更できない。フレンド系の入室基準も含め、この引き継ぎ方法は実装前に確定する。
- 閉じた同一ルームからの復旧には共通の再作成キーを使い、複数人・複数タブ・複数Podの同時再接続でも作成を1回にまとめる。
- 最初に作成が成立した人が新インスタンスの作成者・最初のオーナーになる案。ほかの人をどの条件で同じ新ルームへ案内するかは、入室条件と合わせて確定する。古い在室証明だけで新しい公開範囲を無条件に通過させない。
- ロード中は操作を止め、新しい接続とIDが確定してから表示・共有リンクを切り替える。失敗時は再試行か、新しいルームの作成へ進めるようにする。

## 6. 対戦席と交代

入室後に盤面や共通メニューからデッキを選び、盤面の空席を選んで座り、両者が準備完了すると開始する。デッキ選択と着席はどちらからでも行える。観戦から対戦への移動に別ページや再入室ロードは挟まない。

| 場面 | できること |
| --- | --- |
| 対戦前 | 観戦・待機者が盤面の空席を選んで座る。着席者は席を立つ、デッキを選ぶ、準備完了を取り消す |
| 対戦中 | 着席者は対戦し、ほかの入室者は同じ盤面を観戦する。進行中の対戦席に別の人は座れない |
| 対戦終了後 | 結果を確認して「席を維持して次の対戦へ」か「席を空けて観戦へ」を選ぶ。空いた席には観戦者が盤面から座れる |

- 席を立つ操作と、ルームから退出する操作を分ける。席を立っても部屋には残る。
- 空席には盤面上で参加できることを見た目と短い動きで示す。席が埋まっている間は観戦のままにし、対戦終了後に席が空けば同じ場所から参加できる。
- 同じ席を同時に選んだ場合は、先に成功した1人だけが座れる。
- 席が変わったら、その席のデッキと両者の準備完了を解除する。前の人のデッキを次の人へ渡さない。
- ルームオーナーでも、対戦中の人を別の人に入れ替える権限は持たせない。
- 対戦中に自分で席を立つ・退出する場合は、投了になることを示してから処理する。
- 試合終了時に席を自動で空けない。本人が観戦を選んだら席を解放し、席を維持したら次の試合に向けてデッキ・準備を操作できるようにする。準備完了は新しい試合に持ち越さない。
- 通信断は明示的な投了と分ける。ほかの在室者がいる間の席の保持期限・切断決着は未確定。フリーマッチの1分切断敗北をそのまま流用しない。
- 通信断で空いたように見える席には、対戦の終了と席の解放が確定するまで別の人を座らせない。交代待ちの列は別の拡張とする。

### CPUを呼んで、そのまま対戦する

起動時に入ったルームでも訪問先のルームでも、盤面または共通メニューの「CPUを呼ぶ」から空席へCPUを置けるようにする。自分がもう一方の席に座れば、画面を移動せずその部屋でCPU戦を始められる。観戦中の人も同じ試合を見られる。別の人がCPU相手に遊び、自分は観戦することもできる。

初期案:

- CPUは対戦席の相手として盤面に表示する。ログインした人間や招待された入室者としては扱わず、オーナーになれない。**CPUだけが残っても在室人数は0なので、ルームを閉じる。**
- 一度に呼べるCPUは1体まで。空席がない、または対戦中なら新たに呼べない。席の確保はサーバー側で確定し、人が同じ空席を選んだ場合に二重着席させない。
- 呼ぶときに既存の難易度から選ぶ。CPUのデッキは部屋のルールに合うものを使い、対戦開始時にほかのデッキと同じ検証を通す。細かなデッキ指定は追加判断とする。
- CPUを呼んだ人がデッキを選ぶ間も、その部屋とフレンド・招待・共通メニューは使える。CPU対戦用の別ルームや別ページを作らない。
- 人間が入室しても進行中のCPU戦は続く。その人は観戦でき、試合が終わった後にCPUと席を交代できる。対戦途中の席の差し替えはしない。
- 対戦前と終了後はCPUを席から外せる。対戦中にCPUを外したい場合の終了処理は、履歴・勝敗への影響と一緒に決める。

オンラインルームの盤面は現在もルームサーバーが管理する。CPUの判断にも既存の [CPUの仕様](cpu.md) とgame-coreの合法手・カードルールを使い、ルーム内では**サーバーがCPUの操作を決定・検証して同じ盤面へ配信する**設計にする。観戦者やCPUを呼んだブラウザにCPUの操作権限や相手の未公開情報を預けない。CPUの思考で対人の操作やほかのルームが止まらない実行方法・計算量上限は実装時に決める。

現在の「さいきょう」は配信モデルをブラウザが使う。ルームサーバーで同じ難易度を提供するには、モデルの取得・更新方法を別途整える必要がある。初期対応の難易度とモデル取得失敗時の扱いは未確定とする。

## 7. ルール変更と観戦

カードのルール・デッキ検証は [ルール・裁定集](game-rules.md) と既存のgame-coreに合わせる。ルームの変更に伴ってカード効果を変更しない。

ここで変えるのは次の試合のルール。ルーム作成時に固定した名前・公開範囲・作成者は変更しない。

初期案:

- 対戦前にオーナーがルールを変えると、両者の準備完了を解除し、デッキを再検証する。
- 対戦中に変えたルールは次の対戦から使う。実行中の対戦は開始時のルール・持ち時間を保持する。
- 現在の対戦のルールと次の対戦の設定を分けて持ち、観戦・共有で取り違えない。
- 入室できることと、観戦で非公開カードまで見られることを分ける。オーナーも対戦席を持たなければ観戦者と同じ情報だけを受け取る。

現在の通常ルーム観戦は両者の手札を公開する。人が自由に集まる新ルームでは、**観戦の標準は手札非公開にする案**を推奨するが、ユーザー確定事項ではない。手札公開の練習モードを設けるか、観戦不可の設定を残すかは別途決める。対戦中に手札公開を有効化する変更は、初期実装では扱わない。

## 8. どこからでも開ける共通メニュー

起動時に入ったルームの盤面をゲームの起点とし、フレンド・デッキ・CPUの呼び出し・プロフィール・通知・設定などを共通メニューから呼び出す。どのルームでも、対戦・観戦、盤面エディタなどゲーム内の各画面でも同じメニューを開ける。背景に今いる部屋や作業中の盤面を残し、その上に表示する。

- Escキーまたはメニューボタンで開く。スマートフォンでもメニューボタンを常に使える。
- Escは最前面のカード詳細や確認ダイアログから閉じる。閉じるものがないときに共通メニューを開く。文字入力中の操作や日本語変換と競合させない。
- メニューの先頭で、現在の部屋・フレンド・招待や共有へすぐ進める。どのルームからも同じ機能にアクセスできるようにする。
- 新規作成の操作は「ホームへ戻る」と呼ばない。機能は現在の部屋から退出し、別IDのルームを作って移動すること。短い表示名とアイコンで新規作成・移動を伝え、対戦中なら投了、オーナーなら不在化の影響を示す。アイコンの具体形は確認後に確定する。
- デッキ選択もこの共通メニューから呼び出せる。選び終えて閉じると元の盤面へ戻り、準備状況を反映する。実行中の対戦に使うデッキは変更しない。
- 「CPUを呼ぶ」は現在のルームの空席にCPUを置く操作。難易度を選んで閉じると、そのまま今の盤面で準備や観戦を続けられる。
- 設定から、新しく作る部屋の種類を変更して保存できる。初期値はインバイトとする。
- メニュー内の画面切り替えでルームのWebSocket、在室、対戦状態、演出待ちを破棄しない。閉じれば元の場面へ戻る。
- メニューを開いても対戦・持ち時間は止めない。自分の番、残り時間、再接続中の状態は分かるようにする。
- 背景の盤面へクリックやキーボード操作を通さない。開閉時のフォーカスを管理する。
- 別ルームへの移動など、今の対戦を離れる操作は単なるメニュー内移動と区別し、退出・投了の影響を表示する。

接続の保持は `/game/` の共有レイアウト配下など、個々のメニュー画面や準備画面・盤面の切り替えでは破棄されない場所に移す案。既存の `GameMenu` と各ページの中身を再利用し、起動時のルームと訪問先のルームに別々の機能を作らない。

見た目は [デザイン基準](design-system.md) に合わせる。`src/app/brand.css` の変数と共有フォントを使い、アイコン・短いラベル・アバター・小さな動きで伝える。添付されたランチパッド画像は開き方や操作構成の参考とし、配色はぷぷりえーるに揃える。

## 9. 入室のロード画面・URL・共有

### 起動ロードとルーム間の接続表示

| 経路 | 表示 | 入室後 |
| --- | --- | --- |
| `/game/` から起動 | ロゴ付きの全画面起動ロード | 有効な在室ルーム、または新規ルームの盤面 |
| 招待・共有URLから直接起動 | ロゴ付きの全画面起動ロード | 指定ルームの盤面 |
| ルームAからルームBへ移動・新規作成 | 現在の盤面を背景に残す軽い接続表示 | 移動先の盤面 |
| 一時切断から元のルームへ再接続 | 現在の盤面上に小さな再接続表示 | 同じ盤面を復元 |
| 無人閉鎖後に別IDのルームへ再作成 | ロゴ付きの全画面起動ロード | 新しいルームの盤面 |

全画面の起動ロードはモーダルではなく、盤面の前に表示する独立した画面。上部に `public/pupu_game.webp` のロゴを置き、中央にランダムな既存カードの絵・名前・短い紹介を表示する。読み込みが続く間は星やカードに控えめな動きを付け、進捗バーや根拠のないパーセンテージは表示しない。カードはロード開始時に1枚選んで固定し、通信中に何度も入れ替えない。効果を説明する文は [ルール・裁定集](game-rules.md) と一致させる。

招待・共有URLから直接起動する場合は、入室権限の確認後にルームのサムネイルをカードの近くに見せ、どの部屋へ向かうか分かるようにする案。サムネイルはリーサルパズル一覧と同じ16:9の盤面プレビューの見せ方を使い、共有カード・OGPにも同じルール別画像を使う。権限確認前には非公開ルームの名前・在室者・専用画像を出さず、共通の起動画面のままにする。現在の対戦画面をその場で撮影して非公開カードを写さない。

ルーム間の移動では、今の盤面を見せたまま小さな接続表示と移動先のアイコン・名前を出す案。対戦操作や二重入室を防ぎ、移動先への入室権限を確認してから元のルームを退出する。失敗した場合は元のルームにとどまり、理由と再試行を示す。接続確定後にだけ移動先の盤面とURLへ切り替える。

どの表示も実際の接続が済めば直ちに消し、演出のためだけに待ち時間を追加しない。失敗時は理由と再試行を示し、入室できないURLでは新しいルームを作る導線も置く。キーボード・スクリーンリーダーには現在の工程を短い文で伝え、動きを減らす設定では繰り返すアニメーションを抑える。同じルーム内のデッキ選択、CPUの呼び出し、対戦開始、観戦と着席の切り替え、共通メニューの開閉には入室ロードを挟まない。

### URLの役割（提案）

**今の `/game/` はゲーム起動の入口として残し、入室した通常ルームの盤面へ進める。** 有効な在室セッションがあれば復帰し、なければ新規作成する。入室が確定したらブラウザのURLも `/game/room/<roomId>/` に切り替える。`/game/` 自体は部屋の共有リンクにしない。現在いる部屋を共有するときは、起動時に作った部屋も訪問先の部屋も、そのルーム固有のURLをコピーする。

| URL | 開くもの・共有時の意味 |
| --- | --- |
| `/game/` | ゲーム起動の入口。有効な在室があればその部屋へ復帰し、なければ設定した種類で通常ルームを作る |
| `/game/room/<roomId>/` | 1つのルームへの共有リンク。入室ロード後、待機・観戦・対戦を同じ盤面で表示する。試合が始まってもURLを変えない |
| `/game/match/<matchId>/` | その試合を指す共有リンク。進行中は入室権限を確認して試合のあるルームへ、終了後は閲覧権限を確認して結果・リプレイへ案内する案 |

インバイト／インバイト＋でコピーするURLは、ルームURLに入室権限を示す秘密の値を付けた形を想定する（例: `/game/room/<roomId>/?invite=<token>`）。相手を限定したURLでは、秘密の値とログイン済みの指定相手の両方を確認する。パブリック・フレンド・フレンド＋のURLは、この値を付けずに案内できる。どのURLも部屋が閉じたら失効する。

初期実装で必須なのは起動入口とルーム固有のURL。個別の試合URLは、進行中の試合IDからルームを探す方法と、終了後の履歴への案内・閲覧権限を整えて追加する。試合のURLが未完成でも、進行中の対戦はルームURLで共有できる。後日ほかの試合が始まっても、ルームURLはそのルームの現在の状態を開く。一方、試合URLは特定の試合を指し続ける。

現在は `/game/battle/room/?id=…` が準備・招待リンク、`/game/room/?id=…` が対戦盤面で、対戦開始や終了時に相互に移動する。新しい設計では両方を `/game/room/<roomId>/` にまとめる。既存の共有リンクは新URLへ転送し、`watch=1` は入室後の観戦希望として引き継ぐ。ただしサーバー側の入室・観戦権限は別途確認する。閉じた部屋の古いリンクは閉鎖画面に進め、新しい部屋を自動作成しない。

招待・共有URLから直接開いた起動ロードはリンク先URLで表示できる。ロード専用の共有URLは設けない。これによりDiscordで共有するURL、入室後の画面のURL、OGPが同じルームを指す。

### フレンドの現在地とサムネイル

パブリック・フレンド・フレンド＋のルームは、入室条件を満たすフレンドの現在地を在室者としてまとめて表示する。対戦席が埋まっていても入室はでき、部屋の空きと対戦席の空きを分けて表示する。インバイト・インバイト＋のルームは、フレンドが入っていてもソーシャルのルーム一覧や現在地には表示しない。

ソーシャルのルーム詳細には、参考画像のようにルーム名と「作成者」を表示する。作成者は作成時に確認したアカウントID、またはゲストの識別情報として固定する。ログインしている作成者の名前・アイコンはその人のプロフィールから表示し、ゲスト表示は作成時の名前を使う案。オーナーが交代しても作成者欄の人は変えない。現在のオーナーを示す場合は管理役として別に表示し、不在なら不在と分かるようにする。インバイト型の詳細は招待された人だけが開ける。

共有リンクを開いた未入室者には、ルームのサムネイル・名前・公開範囲・ルール・入室ボタンを見せる案。対戦者数と観戦・待機者数は短く添える。参加後は同じURLの盤面へ進み、席の操作で役割を決める。通常リンクと観戦専用リンクに分ける必要性も見直す。

- サムネイルはルールの組み合わせから選ぶ。ルームごとの画像アップロードは初期範囲に含めない。
- OGPと画面内のルームカードで同じサムネイル選択処理を使う。
- OGPはリンクを開く前のプレビュー、入室ロードは本人の画面として、公開可能な情報をそれぞれ確認する。招待トークンは画像・タイトル・説明文に含めない。
- 初期案では「次の対戦に使うルール」をルームサムネイルの基準とし、対戦中のルールは別表示にする。
- 権限なしで取得されるOGPには、公開してよい情報だけを返す。非公開ルームは共通画像・共通文言を使う案とし、名前や在室者を漏らさない。
- 閉じたルームへのリンクでは、閉鎖したことを表示する。古いリンクを開いただけで別ルームを作ったり、自動転送したりしない。
- 再作成後は新しいURLを共有する。前のルーム・招待URLは失効し、新しい部屋を自動的に追わない。ソーシャルには公開範囲が許す部屋だけを表示する。インバイト型では新しい招待が必要。

## 11. 実装の順序と確認項目

1. 入室者・所有権・席・試合を分離し、無人閉鎖と再接続の土台を作る。
2. 公開範囲・フレンド判定・招待と作成時の部屋の種類の保存を追加する。初期値はインバイトとする。
3. 起動時に通常ルームの盤面へ入り、デッキ選択、オーナー取得、着席・離席、対戦後の席交代、ルール変更、CPUの呼び出しができるようにする。
4. ゲーム内の各画面で共通メニューをEsc・メニューボタンから開けるようにし、フレンドの現在地表示も更新する。
5. ルーム固有のURL、旧リンクからの転送、ロゴ・カードを使う全画面の起動ロード、ルーム間の軽い接続表示、ルール別サムネイル、OGPを追加する。試合固有のURLは試合と履歴を結ぶ参照を整えてから追加する。

実装では、まず以下を確認する。これは今後の受け入れ条件であり、現時点で検証済みという意味ではない。

- 在室セッションがなく設定も未設定でゲームを開くと、インバイトの通常ルームを作成し、その盤面に自分が表示され、そこからデッキを選べる。作られた部屋は同じURLで他人も入室でき、共有リンクから作った部屋と入室条件・所有権・寿命・席・CPUの挙動が同じになる。
- 起動時に入ったルームからCPUを空席に呼び、同じURL・盤面・接続のまま準備、対戦、結果確認まで進められる。ほかの入室者は観戦し、終了後にCPUと交代できる。
- 人が全員いなくなるとCPUが残っていてもルームが閉じ、空席への同時着席やCPUの操作の重複も起きない。
- 設定で保存した部屋の種類が、開き直した後やメニューからの新規ルーム作成にも適用される。保存だけで在室中の部屋を変更しない。
- 招待・共有リンクから開いた場合、不要な別ルームを作らず目的の部屋へ進む。
- `/game/` と招待・共有URLからの直接起動では、全画面にロゴとランダムな既存カードの絵・短い紹介を表示し、バーを使わず、接続が済めばすぐ盤面へ進む。招待先のルームサムネイルは権限確認後にだけ見せる。
- ルームAからルームBへ移るときは軽い接続表示を使い、移動先への入室に失敗したら元のルームにとどまる。無人閉鎖後の別IDへの再作成では全画面の起動ロードを表示する。
- `/game/` は有効な在室ルームへ復帰するか通常ルームを新規作成し、共有操作は現在の部屋固有のURLを渡す。ルーム内の待機・観戦・対戦でURLは変わらず、古い準備・盤面リンクも同じ部屋へ着く。
- メニューの新規作成操作では現在の部屋を退出して別IDのルームへ入り、以前の部屋に残った人やオーナー権限を奪わない。単なる再読み込みなら有効な在室セッションを復元し、部屋を増やさない。
- 起動時に入ったルーム・ほかの人のルーム・対戦・観戦・CPU対戦・盤面エディタで共通メニューを開閉でき、元の状態へ戻れる。
- 作成者が席に座らず、ほかの2人の対戦を見られる。
- 観戦・待機者は対戦前と試合終了後、盤面上の空席を選んで座れる。試合中の席は差し替えず、試合後の対戦者は席を維持するか、席を空けて観戦に移るかを選べる。観戦と着席の切り替えでURLや入室状態を失わない。
- 対戦者が全員抜けても観戦・待機者がいれば残り、最後の1人が抜けるとほぼすぐ閉じる。
- オーナー退出後は不在になり、同時に複数人が取得しても1人だけ成功する。
- オーナーが別の人へ移っても、部屋の作成者・名前・公開範囲は変わらない。ソーシャルのルーム詳細は元の作成者を示し、現在のオーナーとは混同しない。
- ルーム作成後の公開範囲・名前の変更を拒否し、オーナーが変えられるのは次の試合のルールだけにする。
- 席交代で前の人のデッキ・準備完了・操作権限を引き継がない。
- フレンド＋の起点から退出者が外れる。オーナー変更・不在時も定義した入室条件になる。
- 5種類の公開範囲を、一覧・直接URL・API・WebSocketで一貫して適用する。
- フレンドルームは作成者のフレンドだけが入れる案。オーナーが変わっても対象は変わらない。インバイトはフレンドでも招待なしでは入れず、オーナーが渡したURLを知る人が入れる。限定URLは指定相手だけが使える。
- インバイト・インバイト＋の部屋はソーシャルに出ない。招待URLのないフレンドは招待をリクエストし、許可されてから入れる。
- 閉鎖したルームの共有・招待URLでは新ルームに入れず、新しいルームへ自動転送されない。
- メニュー操作で在室や対戦を失わず、持ち時間が継続し、背景の盤面へ誤操作が届かない。
- 生きている接続が別タブ・別Podにあるときは閉鎖しない。入室と無人閉鎖、所有権取得と退出の競合でも整合性を保つ。
- 無人閉鎖後の同時再接続でルームを重複作成せず、ロード後に新しいIDへ切り替わる。
- 明示的な退出や古い共有リンクへの訪問で、自動再作成しない。
- ルーム閉鎖後も対戦履歴を読めて、復旧処理が閉鎖ルームを復活させない。
- スマートフォン、漢字を含む日本語、キーボード操作、動きを減らす設定で表示と操作を確認する。

## 12. 実装前に詰めること

| 項目 | 現時点の整理 |
| --- | --- |
| 起動時に入ったルームの初期表示 | 盤面に自分がいることと、そこからのデッキ選択は確定。自分の見せ方や初期の着席状態を詰める |
| 新規ルーム作成のアイコン | 「ホームへ戻る」と誤認させず、新規作成と移動を直感的に伝えるSVGを詰める |
| 作成時の部屋の種類の保存 | 設定で選んで保存し、未設定はインバイトで確定。アカウント・ゲスト・端末間同期の分担を詰める |
| 無人閉鎖と接続期限の秒数 | 無人確定後はほぼ即時。通信断の検知時間と分けて決める |
| 閉鎖後の再作成 | ロードを挟んで新ルームへ移る方針は確定。設定・新オーナー・元の在室者を再参加させる条件を詰める |
| オーナー変更時のフレンド基準 | 作成者のフレンドを基準に固定する初期案。作成者表示の固定と一緒に、この入室基準も確認する |
| ルーム定員 | 対戦席2席と、ルーム全体の上限を分けて決める |
| ゲスト | 作成・オーナー取得・各公開範囲での参加可否、同一人の識別を決める |
| 招待リクエストのUI | ルーム情報をソーシャルに表示せずに、誰へリクエストを送るか、承認・拒否と通知をどう見せるかを決める |
| 招待URLの細部 | URL共有だけで入れることと、指定相手だけに限定できることは確定。リンクの期限・取消・利用回数などの細部を決める |
| 対戦中の通信断 | ほかの在室者がいる場合の席保持・敗北判定と、全員不在時の中断記録を決める |
| 観戦 | 手札非公開を標準とする案。練習用の手札公開・観戦不可の設定を決める |
| 席交代 | 試合後に席を維持するか観戦へ移るかを選ぶ。交代予約と切断中の席解放期限は追加判断 |
| 試合固有のURL | 進行中の試合IDからルームを引く方法、終了後の履歴・リプレイの権限と案内先を決める |
| CPUの呼び出し権限 | 在室者の誰が呼べるか、オーナーが許可・停止できるかを決める |
| CPUの難易度・デッキ | 初期対応の難易度、さいきょうのモデル取得、デッキ選択範囲を決める |
| 対戦中のCPUの退出 | 途中で外す操作の可否と、その際の勝敗・履歴の扱いを決める |
| 名前と管理操作 | 作成時の名前の文字数、ゲスト作成者の表示、キック・ブロックなどの範囲を決める。作成後の名前・公開範囲変更は不可 |

## 13. 実装計画（2026-10-24）

連絡・待ち合わせはDiscordで行う前提とし、ゲーム内チャットは作らない。「Discordに貼る → リンクを開く → 盤面に着く → 空席をタップ → 準備OK」を最短の導線にする。各段階でテストとブラウザ確認をしてから、ブランチ `feat/social-rooms` にコミットする。

| 段階 | 内容 | 主な変更先 |
| --- | --- | --- |
| 1. ルームの土台 | 入室者・作成者・オーナー・席・試合を分けたルーム（`plaza`）。部屋の名前・公開範囲は作成時に固定。入室者単位の接続、離席・着席・準備、オーナー不在と取得、ルール変更（対戦中は次の試合へ）、無人閉鎖、閉鎖後の後継ルーム、サーバーが操作するCPU席 | `packages/game-core/src/room.ts`、`services/room-server/src/{rooms,plaza,cpu,backend,server}.ts` |
| 2. 起動と盤面 | `/game/` は起動入口（全画面ロード→在室ルームへ復帰、なければ作成）。`/game/room/<id>/` に待機・観戦・対戦を統合。接続は `/game/` の共有レイアウトで保持し、旧URLは転送 | `src/app/game/`、`src/components/game/plaza/`、`src/lib/game/room/` |
| 3. 共通メニュー | Esc・メニューボタンで開くランチパッド。招待（Discord用コピーを先頭）、CPUを呼ぶ、デッキ、フレンド、設定（新しく作る部屋の種類）、新しいルーム | `src/components/game/launchpad/` |
| 4. フレンドの現在地 | 公開範囲が許すルームだけ、フレンドの在室を自動で表示。フレンドへの招待・招待のリクエストと承認 | `src/lib/game/social.ts`、`src/components/game/social/` |
| 5. 共有画像 | ルール別のサムネイルをOGPとルームカードで共有。非公開ルームは招待リンク以外では共通の文言・画像 | `src/app/api/og/room/`、`src/app/game/room/[roomId]/` |

### 実装で決めたこと（12章の初期値）

| 項目 | 決定 |
| --- | --- |
| 起動時の自分 | 席には座らず、盤面のまわりの在室者に自分のアイコンを出す。空席をタップすると「すわる」「CPUを呼ぶ」 |
| 部屋の種類の保存 | 端末（localStorage）に保存。未設定・読み取り失敗はインバイト |
| 不在の判定 | 接続が切れてから2分で不在（スマホでDiscordへ切り替えてリンクを貼る間に閉じないため）。明示的な退出は即時。作成から最初の接続までも同じ2分 |
| 無人閉鎖 | 不在が確定して入室者が0人になったら即時に閉じる。CPUは人数に数えない |
| 閉鎖後の再作成 | 閉じたルームの入室者だった証明（入室トークン）で、名前・ルール・公開範囲を引き継いだ別IDのルームを作る。同じ旧ルームからの再作成は後継ルーム1つにまとめ、旧ルームの入室者だけが後継へ入れる。古い共有リンクの訪問者には作らない |
| オーナー | 作成者が最初のオーナー。退出・不在の確定で不在になり、在室者の誰でも「オーナーになる」を押せる（先着1人） |
| フレンド判定 | フレンドは作成者のフレンド、フレンド＋は作成者または在室者のフレンド。ログインが必要 |
| ゲスト | 作成・オーナー取得・パブリック／インバイト系への参加はできる。フレンド系の部屋と相手限定の招待は使えない |
| 定員 | 対戦席2、ルーム全体16人 |
| 招待URL | 部屋ごとに1つの秘密の値（`?invite=`）。インバイトはオーナー、インバイト＋は在室者が共有できる。オーナーは作り直して旧URLを失効できる。期限・回数の制限は設けず、部屋が閉じたら失効 |
| 相手を限定した招待 | フレンドを選んで招待すると、その人のアカウントだけを許可し、プッシュ通知とソーシャル画面で知らせる |
| 招待のリクエスト | フレンドの相手にリクエストを送り、インバイトではオーナー、インバイト＋では在室者が盤面で許可・見送りを選ぶ。部屋の名前・IDは許可されるまで見せない |
| 対戦中の通信断 | 不在が確定したら、その席の投了として記録する |
| 観戦 | 手札は非公開（フリーマッチの観戦と同じ見え方）。手札公開の練習モードは扱わない |
| 席交代 | 対戦後は「この席でもう一度」か「席を空けて観戦」。交代の予約列は扱わない |
| CPU | 在室者の誰でも、対戦していない間に空席へ1体呼べる。強さは4段階（さいきょうはアプリ内蔵のモデル）、デッキはルールに合うおまかせ。対戦中は外せない |
| 名前 | 16文字まで。キック・ブロックは扱わない |
| 試合固有のURL | 今回は扱わない（ルームURLで共有する） |

### 未実装として残すもの

- アカウント間で部屋の種類の設定を同期すること。
- 試合固有のURL、交代の予約列、キック・ブロック、手札公開の練習モード。
