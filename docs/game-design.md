# 対戦ゲームの設計

## 現在の構成

既存の Next.js サイトに `/game/` を追加し、対戦ルールを pnpm workspace の `@pplale/game-core` に分離する。リポジトリは共有し、Firebase・Vercel を利用する構成。実際のプロジェクト設定や本番稼働状況は今回の確認対象に含めない。実装との照合とテストの結果は [検証記録](verification.md)。

```text
src/data/*.json ── catalog.ts ──> game-core
/game/ ──> 起動画面 ──> /game/room/<id>/ ──> 待機・対戦・観戦
                          ↑ 共通レイアウトが接続を維持
                          └─ launchpad/ ──> 各画面を重ねて表示

CPUの単独対戦・リプレイ・エディタ ──> BoardEmulator
                               └─ 単独対戦の途中保存は localStorage
```

| 層 | 責務 | 場所 |
| --- | --- | --- |
| Next.js | ルート、カード画像、ログイン、Firebase の保存済みデッキ読み込み | `src/app/game`, `src/lib/game` |
| 画面 | 操作の状態とルール（`board/useBoard`）、盤面の各領域（`table/`）、パネル（`panels/`） | `src/components/game` |

### コードの追い方とコメント

各ファイルの冒頭には責務を日本語で短く書く。公開型では、値の単位・公開範囲・再接続時の扱いなど、型だけでは分からない条件を補う。コードを読み上げるだけのコメントは増やさず、再送しない理由や秘密を公開しない理由を残す。識別子は意味を追える英語を使い、短い省略名や多段の三項演算子に処理を詰め込まない。

画面は操作と描画、サーバーは権限と確定状態、game-coreはルールと共有型を担当する。同じ表示や判定を別の画面に複製しない。学習済み係数・自動生成データは生成元から更新し、可読性の整理で値を変えない。

### 分離する価値

- ゲーム本体は React / Next.js / Firebase / DOM に依存しない。UI の更新やホスティングを変えてもルールを持ち運べる。
- 人間と CPU は同じ `applyCommand` を通る。PP、不正な対象、手番などの判定を画面ごとに重複実装しない。
- ゲーム本体は元の状態を変更せず次の状態を返す。状態内の乱数 seed により、同じ入力とコマンド列で同じ結果を再現できる。
- 「効果の対象を選ぶ」途中も状態として保存できる。ルーム対戦の通信層でも利用する。

分離の単位はライブラリ。game-core は同じリポジトリの Web アプリ・CPU サーバー・ルームサーバーから利用する。サーバーはそれぞれ別プロセスとして実装されている。

## 対戦の開始とドロー

`GameState.phase` は `dice` → `initiative` → `opening` → `mulligan` → `playing`。ダイスと先攻決定は core、演出は UI が扱う。開始ダイスは引き分けなし・選択権の確率50%ずつとし、`decisiveOpeningDice` の有無で旧リプレイの乱数を維持する。CPUの学習用レポートにも同じ区別を含める。初期ドローは `openingRemaining` と `openingDraw` Command で各側を独立して管理する。双方が相手を待たずに山札を選んで引ける。通常ドロー・カード効果・10/5のドローは `pending` に保持し、山札クリックの `choose` Command ごとに1枚引く。解決待ちの間はプレイやターン終了を拒否する。先攻3枚・後攻4枚を引いた後、`mulligan` / `keep` Command で各初期カードを1回だけ交換し、双方が確認して対戦を開始する。CPU も同じ Command を使用する。

UI はドロー前後の手札と山札の差分から移動演出を描く。2026-10-31のテンポ調整で、ダイスは移動800ms・開始時の結果表示350ms・CPUの開始ダイス待ち150ms、ドローは移動360ms・着地80msとする。演出と操作ロックは同じ時間を使い、1タップにつき1枚、着地前の連打は予約せず無視する。詳細はサイドパネル、効果の対象は場や手札、山札を直接操作する。保存キーは維持し、旧セッションは進行中の `playing` 状態として復元する。

## Vercel への配置

- Root Directory はリポジトリのルート。既存 Next.js プロジェクトのまま運用する。
- `pnpm install --frozen-lockfile` で root と3つの workspace（game-core・CPU サーバー・ルームサーバー）の依存関係をインストールする。root の `pnpm-workspace.yaml` と依存関係、共有 `pnpm-lock.yaml` に登録済み。
- Build Command は既存の `pnpm run build`。`transpilePackages` により game-core の TypeScript を Next.js がコンパイルする。core の `dist` を事前生成・コミットする必要はない。
- ローカルと CI は Node.js 26.12.1、Vercel は Node.js 24.x でビルドする。`engines.node` を `24.x || 26.x` にして、Vercel が未対応の 26 を選ばず、利用可能な 24.x に解決されるようにしている。
- Firebase の環境変数と AuthProvider は既存のものを使用する。同一ドメインなら同じログイン状態で保存済みデッキを選べる。
- Vercel に常駐プロセス、WebSocket サーバー、対戦用 API は追加していない。CPU / 同一端末対戦はブラウザで動く。
- `NEXT_PUBLIC_ROOM_SERVER_URL` を設定すると、ゲームの起動時のルームがそのルームサーバーにつながる。未設定なら起動画面に「つながりません」と出て、CPU対決（`/game/cpu/`）だけ遊べる。詳細は [services/room-server](../services/room-server/README.md)。
- `NEXT_PUBLIC_CPU_SERVER_URL` を設定すると、「さいきょう」は CPU サーバーのモデルで考え（思考はブラウザのまま）、同意したプレイヤーの対戦記録をそこへ送る。未設定ならアプリ内蔵のモデルを使い、何も送らない。詳細は [services/cpu-server](../services/cpu-server/README.md)。

参考: [Vercel Monorepos](https://vercel.com/docs/monorepos)。Next.js の設定はインストール済みパッケージの `node_modules/next/dist/docs/` に合わせる。

## データとセッション

カード ID と原文は既存 JSON を使う。アダプターが画像を除いたカタログを core に渡す。Firebase の `users/{uid}/decks/{deckId}` から `yojoDeckIds` / `sweetDeckIds` / `playableCardId` を読み、対戦開始時に検証する。読み込み専用で保存デッキを書き換えない。

**対戦のルールとデッキの出どころ。** 対戦のルール（`packages/game-core/src/rules.ts` の `MatchRules`）は、デッキに使えるカードの範囲：フルーツの環境（いちご／＋ぶどう／＋メロン／＋オレンジの4つ。`fruitsUpTo`、受け取ったルールは `parseMatchRules` がこの形にそろえる）と、拡張プレイアブル（ExP）の可否。CPU対決の準備とルームの作成で、同じタイル（`src/components/game/RulePicker.tsx`）から選ぶ。選べる範囲は `playableNow`（実装済みのフルーツ・プレイアブル）から決まり、それ以外は「準備中」と出る。デッキの出どころは `src/lib/game/deckSources.ts` にまとめる：おためし / おまかせ（`randomDeck`：ルールに合う実装済みカードから幼女20枚・お菓子10枚とプレイアブルを選ぶ。枚数制限を守り、足りるかぎり同じカードは2枚まで）/ 保存済み。それぞれがルールに対して「選べるデッキと、選べない理由（`deckRuleErrors`）」を返し、CPU対決の準備とルームのページは同じ選択欄（`DeckSelect.tsx`）でそれを並べる。出どころを足す（2pick で作ったデッキなど）ときは `deckSources` に足せば両方に出る。

対戦途中は `pplale-game-session-v2` に自動保存する。同一ブラウザ・同一オリジンで再読み込み後に再開できる。進行中の対戦にはデッキの実体と選択したルールが保存される。あわせて、開始時の設定（`setup`：両者のデッキ、進め方のルール、準備で選んだ対戦のルール `matchRules`。選べるようになる前の保存には `matchRules` がなく、そのまま読める）、最初の状態（`initial`）、適用した全コマンド（`commands`）も保存する。再戦は `setup` から新しい seed で作り直し、リプレイは `initial` に `commands` を順に適用して再生する（core は決定的なので同じ結果になる）。リプレイ中は保存を行わない。保存形式の変更、ブラウザのデータ削除、別ドメイン・別端末への移動では再開できないことがある。ルールコード自体の版を固定した長期保存は未実装。

## サイトとゲームのProvider

`SettingsProvider`はデッキ構築を持つ`src/app/(app)/layout.tsx`でだけ使う。`DarkModeProvider`は`components/site/`にまとめ、通常サイト・プライバシーポリシー・利用規約の各レイアウトで共用する。どちらもゲームには配置しない。デッキ構築の同名カード2枚制限とサイトのテーマ設定はゲームのルール設定から分ける。ゲーム・トップページは固定のブランド配色で、初期化スクリプトもテーマ設定を読まない。サイトから離れると`html.dark`を解除し、保存したサイト設定自体は保持する。`AuthProvider`はルートに残し、同じドメインのプロフィール・デッキを共用する。

## ルーム（オンライン対戦）

ゲーム（`/game/`）を開くと、ロゴとカードを見せる起動画面のあと、このブラウザが入っているルームへ戻る。なければ設定した種類（初期値はインバイト）のルームを作る。ルームのページ `/game/room/<roomId>/` が1つのルームの共有リンクで、待機・観戦・対戦をすべてここで表示する。テーブルの空席をタップして座り、デッキを選んで「じゅんびOK」。両方の席がそろうと同じページで対戦が始まる。テーブルは立体で、対戦の盤面そのもの（空の山札・場・カウンター。`plaza/RoomScene.tsx` が木の机・四本の脚・半透明の灰色の床を同じCSS 3D座標で描き、`plaza/BoardSurface.tsx` が盤面の部品とスタイルをそのまま使う）を横から見た形に置き、席0が左端、席1が右端に立つ。対戦が始まっても床・机・脚を含む `RoomScene` は破棄しない。共通の `BoardTable` を `BoardSurfaceContext` 経由で同じ天板の描画先へ載せ、`useRoomCamera.ts` が同じシーンのカメラを自分の席の手前・真上へ移す。戻るときも同じ机へ引く。モデルの寸法は一度だけ変え、移動はtransformだけを1100ms補間する。移動中は対戦UIと盤面操作を待たせ、完了後に有効にする。動きを減らす設定と対戦途中の直接入室では移動演出を省く。対戦のカードとコードはテーブルにいる間に裏で読み込み、準備中の画面は出さない。始まった時点で読み込みが終わっていなければ、終わるまでテーブルのまま待つ。席に座らない人は両者の手札が見える盤面を観戦する。空席には CPU も呼べる（サーバーが手を決める）。机・床の立体と盤面は別々の合成レイヤーにし、同じカメラ姿勢・同じアニメーション時刻で同期する。Chromeの立体面の描画順によって木の面が盤面を覆わないようにする。仕組みと決めた初期値は [集まって遊べるルームの設計](social-rooms-design.md) の13章と [services/room-server](../services/room-server/README.md) の「集まれるルーム」。

- **接続はゲームのレイアウトが持つ**（`src/components/game/plaza/PlazaProvider.tsx`）。カード・パズル・エディタなどへ移っても在室と対戦は続き、戻れば今の状態を表示する。別のルームへ入るときは、入れたことを確かめてから元のルームを退出する。
- **共通メニュー**（`Launchpad.tsx`）は Esc、メニューボタン（テーブル・盤面のメニュー内）で開く。今のルーム、ゲームの各画面（ランチパッドの中に開き、アドレスは変わらない。`places.ts`）、設定（ホームルームの公開範囲など）、新しいルームを並べる。
- **招待**は Discord に貼るメッセージのコピーを先頭にする。インバイト系のリンクには秘密の値（`?invite=`）が付き、開いたブラウザはそれを保存してアドレスバーから外す。
- 廃止前のフリーマッチと以前の2人用ルーム（`/game/battle/room/?id=` などの古いリンク）は従来の2席のルームのまま同じURLで表示する。古い形式のURLは `next.config.ts` の転送で `/game/room/<roomId>/` へ移る。

```text
ブラウザ ⇄ WebSocket ⇄ ルームサーバー（services/room-server、自宅クラスタ）
  Command →                game-core を完全な盤面で実行
        ← 自分の席から見える盤面（viewFor）
```

- **ルームサーバー**は Vercel ではなく自宅クラスタで動く別プロセス（CPU サーバーと同じ形）。`REDIS_URL` を設定するとルーム状態を Redis で共有し、複数インスタンス間で対戦を継続できる構成。接続・要求回数の制限などは各プロセスにも持つ。Redis 未設定時は開発・テスト用のメモリ保存になり、プロセスの再起動でルームが消える（`services/room-server/src/config.ts`・`backend.ts`）。Web アプリは `NEXT_PUBLIC_ROOM_SERVER_URL` でつなぐ。未設定やサーバーが落ちている間は、バトルのタブにその旨が出てルームを作れない。API、状態の見方（`/stats`）、デプロイは [services/room-server](../services/room-server/README.md)。
- **ルームのルール**（`packages/game-core/src/room.ts`）は、デッキに使えるカードの範囲：フルーツの環境（いちご／＋ぶどう／＋メロン／＋オレンジの4つ）と、拡張プレイアブルの可否。対戦のルール（`rules.ts`）に観戦の可否を足したもの。作成時に CPU対決の準備と同じタイルで選ぶ（観戦だけチェックボックス）。4つのフルーツと拡張プレイアブルはすべて `playableNow` に登録済みで選べる（エンジンが対応していないものがあれば「準備中」と出る）。フルーツは環境の形でしか選べないので、メロンだけのルールはない。デッキは、ブラウザ（使えるデッキの表示）とサーバー（決定）の両方で同じ関数が検証する。
- **席**は、作成・参加のときにサーバーが発行する秘密のトークンで識別する（ブラウザの localStorage に保存）。ログインは不要で、招待リンクを開いて名前を入れればすぐ入れる。保存済みデッキを使うときだけログインする。同じブラウザで開き直せば席に戻れる。
- **盤面はサーバーだけが持つ。** ブラウザは Command と見ている revision を送り、サーバーが席を確かめて game-core で実行する。ターン中は revision が合わない操作を拒否する（初期ドローと交換は双方が同時に進めるので合わせない）。テスト用の Command は受け付けず、`actor` は送り主の席に置き換える。乱数の種と、デッキのカードの並び（uid とカードの対応）はサーバーで決める。
- **各席には伏せた盤面だけを送る**（`viewFor`、`packages/game-core/src/redact.ts`）。両者の山札の中身と順番、相手の非公開の手札、乱数の種、解決待ちの効果、相手が選んでいる選択肢のうち非公開のカードを消した `GameState` で、盤面の UI はそのまま描画できる。伏せたカードの `cardId` は `hidden`。
- **通信**は席ごとの WebSocket 1本（`lib/game/room/client.ts`）。ルームが変わるたびにサーバーがその席の盤面を送り、操作の結果も同じ経路で届く。切れたら自動でつなぎ直し、つながった時点の盤面から続ける。自分や相手の接続が切れている間は画面に出る。
- **盤面の UI は共通。** `useBoard` は `BoardSession` を受け取り、ブラウザ内の対戦（`useGameSession`）とルームの対戦（`useRoomSession`）のどちらでも動く。ルームでは届いた盤面を1つずつ順に見せる：自分の操作の結果はそのまま反映し（ただし相手が手札誘発で答えるかを選んでいる間は、操作の前の盤面のまま見せる。偽ラグも入る。[カード効果の実装状況](card-effect-rules.md)）、相手の操作は CPU の手と同じ演出（プレイしたカードの表示、攻撃の動き、ダイス）を挟んでから反映する。ダイスはサーバーが振り、結果が届いてから転がす。
- **観戦（2人用ルーム）。** 観戦を許可した2人用ルームは、ルームIDを知っている人が席なしで盤面を見られる（`/game/room/<id>/?watch=1`）。集まれるルームでも、入室者のうち席にいない人には両者の手札を公開する。観戦者に届く盤面は両方の手札が表で（`viewFor(state, 'spectator')`。山札は見えない）、どちらの操作も相手の手と同じ演出で見せる。奥の手札はタップで拡大でき、メニューから反対側に回れる。操作はできない。対戦している2人には観戦の可否と人数が見える。本人が別のブラウザで観戦すれば相手の手札を見られるので、既定は観戦なし。
- **投了・再戦・退出。** 対戦中のメニューから投了できる。集まれるルームでは、リザルトで「この席でもう一度」か「席を空けて観戦」を選ぶ。2人用ルームの「もう一度」は2人ともデッキ選択に戻る。

### まだないもの

- 2人用ルームで切断した相手を待つ時間の上限（戻らないときは自分が投了するか退出する）。集まれるルームでは2分の不在で席の投了になる。
- リプレイと、対戦後の相手のデッキの表示（盤面をサーバーが持つため、ブラウザに記録がない）。

## 未確定のルール

先攻3枚・後攻4枚、初期手札の一括交換（交換で引いたカードの再交換は不可）、山札の自由選択はユーザー指定を反映済み。提供された能力説明とFAQは [ルール・裁定集](game-rules.md)、現在の処理と差分は [実装状況](card-effect-rules.md) に記録する。PP上限12・通常ドロー1枚・先攻初回もドロー・山札切れで敗北しない点は、[説明④・⑤の転記](game-rules.md#11-自分のターンとその他のルール説明④⑤) に記載済み。`sandboxRules` という名前だけを根拠に未確定とは扱わない。初期手札の交換で山札へ戻す手順など、資料で指定されていない部分は実装上の選択として区別する。確定した裁定は画面ではなく core に反映する。

### ターン開始の演出

`playing` への移行とターン番号の変更時、中央に手書きフォントの「あなたのターン / あいてのターン」、その下に「先攻 3ターン目 · 3 PP」のように先攻／後攻・その側のターン数・現在PPを表示する。Panda CSS の keyframes で発光ラインと文字を約1.4秒で拡大・フェードアウトし、その間は操作とCPU進行を待つ。交換後のカード移動がある場合は、その演出を終えてから表示する。初期手札の交換中や保存した対戦の復元時には表示しない。動きを減らす設定では拡大を省略する。

### 初期手札の交換画面

交換は2段階。まず戻すカードを種類に関係なく、下段の手札から上段の「交換する」枠へ移して「交換」を押す（タップ、ドラッグ、上下キーで出し入れ）。交換画面が閉じ、戻すカードが手札から山札へ飛んで裏返る。続けて盤面の光る山札を押し、戻した枚数だけ1枚ずつ好きな方から引く（中央に残り枚数を表示）。引き終えるとその側の準備が完了する。何も移さずに「決定」を押せば交換しない。双方の確定後に対戦を開始する。

### 能力名・数字の印

挑発・突撃・防衛などの有効な能力は、ハートなどの記号ではなく大きな日本語の札で表示する。攻撃力の変化は左、HPの変化は右の白い円形おはじきに分け、どちらかが変わっている場合は両方を表示する（例：左+1、右+0）。ダメージ・追加PP・デッキ枚数・スキルコストなどの丸い印は縦横を固定し、楕円への変形を防ぐ。相手側の能力名と数字もこちらから読める向きにする。

通常のカードコストは画像に任せ、現在の `costOf` が印刷されたコストと異なる場合のみ、手札・選択カード・持っているカード・拡大画面に円形の現在コストを表示する。軽減は緑の下向き矢印、増加は赤の上向き矢印で示す。永続軽減とターン限定の軽減を含め、表示値とプレイ可否は同じ計算を使う。

### PPの丸

自分のPPの丸は、その時点の最大PPと同じ個数を描画する。現在PPの分だけ明るい緑、消費済みの分だけ暗い緑にする。7/7では7個すべて明るく、3/7では明るい3個と暗い4個、0/7では7個すべて暗く、0/0では丸を表示しない。ゲーム全体のPP上限の未到達分は描画しない。各円の幅は個数に合わせて計算し、一列に収める。

### UIの依存関係と未使用コード

`components/shared` は `components/game` などの機能別UIに依存させない。ルームの作成・現在地・ルール操作は `game/plaza`、メニューの開閉と画面切替は `game/launchpad` に置く。ルール絞り込みの判定は `lib/game/room/filters.ts`、表示は `shared/room/RoomRuleFilters.tsx` に分ける。旧ルームURLの入口は既存リンクとの互換性に使うため残す。

`pnpm run typecheck` は未使用のローカル宣言・引数も検査する。`pnpm run check:ui` はCSS Modulesの参照切れ・未使用クラスと共通UIの依存方向を検査し、`mise run check` に含まれる。動的なクラス名を使うモジュールは未使用判定を控えるため、削除前には呼び出し元も確認する。
