# プレイ・攻撃の応答速度改善設計

2026-10-18。現行コードを読んだ設計案。実機での操作時間は未測定。下記の時間目標は改善後の実測値ではない。今回は設計のみで、ゲーム実装は変更しない。

その後の実装範囲と計測結果は [対プレイヤー戦の応答改善・計測記録](game-interaction-performance-results.md) を参照。

## 方針

先読みは行う。ただし優先するのは、**操作受付・ルール処理・通信・演出を分け、操作した瞬間に動き始めること**。画像を読み込み済みにしても、現在のタイマーと操作ロックによる待ちは残る。

カードのふわっとした移動、着地の弾み、攻撃の勢い、ダメージ数字は残す。毎回長い演出が終わるまで操作を止める構造を変える。

## 現行コードから分かったこと

| 箇所 | 現在の動き | 対応方針 |
| --- | --- | --- |
| `board/useBoard.ts` の `act` | `animate(command, () => send(command))`。実行・送信のタイミングを演出が決める | 受付時に実行・送信を開始する |
| `board/useBoardAnimations.ts` の攻撃 | 攻撃開始から360ms後に `commit`、720msまで `strike` が残り操作を止める | 判定・通信を攻撃の予備動作と並行させる |
| 同ファイルの相手カード紹介 | 1900ms後に処理を反映、2400msまで紹介が残る | 最新状態の受信と、紹介・盤面表示の進行を分ける |
| 同ファイルのカード移動 | 移動800ms＋着地後200ms＋個別の遅延。手札・場・山札への移動は操作を止める | 着地と操作解禁を合わせ、余韻は独立させる |
| 同ファイルの偽ラグ | 条件を満たす操作の30%で900〜2600ms追加。攻撃では360msも加算 | 秘匿情報保護を独立した待機状態にする |
| `board/useBoard.ts` の `deciding` | 相手の手札反応中は、反応の存在を悟らせないため前の盤面を表示 | 反応待ちの表示方針として維持・整理する |
| `room/useRoomSession.ts` | サーバーの盤面をキューに持ち、演出側が `accept`。送信中・キューありは一律ロック | 通信待ち、未解決の操作、表示待ちを区別する |
| `GameCard.tsx` と手札・移動表示 | Next Imageを使用。手札と飛行カードで `sizes` が異なる | 同じカードで別画像候補が必要になる可能性を調べ、共通化する |
| `board/BoardContext.tsx` | 盤面・選択・演出・形勢を一つのContextで配る | 更新頻度と用途で購読先を分ける |
| `board/useGameSession.ts` | 更新のたびに状態・初期状態・コマンド列をJSON化してlocalStorageへ保存 | 操作の描画を優先し、保存をまとめる |
| `board/useAssessment.ts` | 形勢計算はWorker化済み。ただし状態・全コマンド等を送信し、結果を保存する | 転送・保存の負荷を計測し、差分化を判断する |

攻撃の360msは「処理・送信開始まで」の設定値であり、必ず360ms無反応という意味ではない。攻撃演出自体は先に始まる。自分のカードプレイもすべてタイマー待ちではなく、偽ラグ等に該当しなければ直ちに処理される。

CPU思考と形勢計算はすでにWorkerを使う。ドラッグ中の移動もDOMを直接更新している。これらを最初から作り直す必要はない。ルール処理・再描画・画像デコードがどれだけ時間を使うかは、別途計測する。

## 1. 操作の流れを変更する

### 共通の責務

- **操作受付**：操作IDを採番し、二重入力を同期的に防ぐ。カード・攻撃元・対象の位置と表示用情報をこの時点で確保する。
- **ゲーム状態**：ローカル対戦は `applyCommand`、オンライン対戦はサーバーの盤面を正とする。
- **表示状態**：どの結果をどの順番まで見せたかを管理する。ゲーム状態とは別に進める。
- **演出**：受付・移動・着地・攻撃・余韻を担当する。コマンド送信をタイマーの中に持たない。

状態は概念上 `idle → submitted → awaitingAuthority / awaitingReaction → presenting → idle`。ローカル対戦ではサーバー待ちを省略する。装飾はこの進行とは独立して残せる。

### 自分のカードを場に出す

1. ドロップ・ボタン操作で、即座にカードの移動と配置先の光を出す。選択解除やドラッグ終了でカードが一瞬消えないよう、操作受付時に表示を引き継ぐ。
2. 同時に、ローカルではルール処理、オンラインではコマンド送信を開始する。
3. 結果に合わせて着地・PP表示・対象選択を更新する。オンラインの送信中カードは仮の表示で、PPや場に出た事実はまだ確定しない。
4. 着地後、未解決の選択や反応待ちがなければ次の操作を解禁する。光や粒子は残ってよい。

ぶらんちゃん等で登場が打ち消される可能性があるため、仮のカードで効果を発動させたり次の攻撃を可能にしたりしない。サーバー拒否時はカードを元へ戻し、選択を復元する。

### 自分のカードで攻撃する

1. 対象確定直後に、攻撃元の予備動作・対象への線や光を出す。
2. 同時にルール処理・送信を開始する。現在の「360ms待って送る」をなくす。
3. 結果が着弾タイミングまでに届けば、そのまま確定した攻撃・回避・反応演出へつなぐ。
4. 未確定なら接触前の構えで待つ。HP減少・破壊・勝敗を予測で表示しない。通信待ちと反応待ちは同じ短い待機ループでつなぐ。
5. 攻撃の解決と必要な表示が終わった時点で操作解禁。ダメージ数字や粒子が消えるまで待たない。

通常操作の時間目標は、受付の視覚反応p95で100ms以内、通常のカード着地180〜280ms、攻撃の予備動作80〜120ms・確定後の着弾まで150〜220ms。通信時間、プレイヤーの反応選択、ダイス表示は別に記録する。高速化しても相手カードの内容を確認できるよう、使用済みカードやログから再表示できる導線を保つ。

### 相手の行動・CPU

受信・計算した最新状態は保持し、必要な紹介と表示イベントを順序どおり再生する。相手のカード紹介は短い登場演出と盤面への移動に接続する。紹介の文字を読ませる時間はカード詳細の再表示で補う。

CPUは演出中に確定済み盤面で次の候補を考えられる構成にする。ただし適用は必要な表示・反応が終わってから行い、考え始めた盤面のrevisionが古ければ破棄する。人間が選択中の未確定盤面から次の手を決めない。

## 2. ロックの理由を分ける

現在の `busy` を、次の意味に分けて扱う。

| 状態 | 次のゲーム操作 | カード確認など |
| --- | --- | --- |
| コマンド未確定・送信中 | ロック | 確認可能 |
| 自分の対象選択中 | 指定された選択のみ可能 | 確認可能 |
| 相手の反応選択中 | ロック | 確認可能 |
| カード着地・攻撃解決の表示中 | 必要な区間だけロック | 確認可能 |
| 光・粒子・ダメージ数字の余韻 | 次の操作が可能 | 確認可能 |

最初の改修では、未確定のコマンドを複数送る方式は採用しない。受付時のref等で二重入力を防ぎ、確定したrevisionで次の操作を受ける。移動中カードの座標やクリック対象が確定するまで、そのカードを使う入力は止める。

演出時間はJSとCSSで共有する。`prefers-reduced-motion` では表示だけ短縮してタイマー待ちが残らないようにする。演出の終了・キャンセル・バックグラウンド復帰でロックが残らない完了処理を用意する。

## 3. 事前読み込みは段階的に行う

| 時点 | 優先して準備するもの |
| --- | --- |
| デッキ選択後・マッチング中 | 対戦画面のルート、自分のデッキの盤面用画像、裏面、選択されたプレイアブル |
| 対戦画面へ入るとき | モードに必要なWorkerの起動とready確認。CPUのモデル取得には上限時間と既存の代替モデルを用意する |
| 初期ドロー・マリガン中 | 見えている手札の画像デコード、飛行カードで使う画像候補 |
| 対戦中の空き時間 | 公開された相手カード、生成トークン等の追加資産 |
| カード選択・詳細を開く直前 | 拡大表示用の高解像度画像 |

盤面・手札・飛行カードの `sizes` を表示用途ごとに定義し、Next Imageが生成する `srcSet` と同じ候補を先読みする。必要なら `getImageProps` で生成する。元画像のURLだけをfetchして「準備完了」としない。取得後は対象画像の `decode()` まで進める。

最優先は直後に表示するカードで、自分のデッキ全体はバックグラウンドで少数ずつ処理する。画面幅・DPRが変われば候補を見直す。全カードの大画像・全モードのWorker・詳細パネルすべてを開始条件にすると、起動時間とメモリが増える。

必要最低限の画面・ルール処理・可視画像で対戦を始められるようにし、画像失敗時も枠と裏面で継続できるようにする。オンラインでは相手の非公開デッキや山札順を先読みのために配信しない。画面遷移のprefetchだけではカード画像の取得・デコード完了を保証しない。

## 4. React・保存・サーバーの負荷

これらは計測後に優先順位を決める。固定の演出待ちとは区別する。

- Contextを盤面、選択・入力、演出、形勢に分け、頻繁な演出更新で手札・場全体が再描画される範囲を減らす。
- ルール処理は現在すべてのカードInstanceを複製するため、変更のないカードでも `GameCard` のmemoが効かない更新がある。描画用の値を安定させる方法を先に検討し、coreのコピー方式変更は計測で必要と分かった場合に限る。
- 合法な攻撃対象等はゲームのrevisionに対応して計算し、選択や装飾だけの変更では再計算しない。
- 演出前後の座標取得は読み取りをまとめる。アニメーション中はtransform・opacityを中心に動かし、影やfilterの負荷は実機で確認する。
- 保存は最新状態を一つにまとめ、描画後に実行する。長い対戦ではIndexedDBへの移行を検討する。コマンド履歴の永続化と定期スナップショットで復元できる構成にし、終了・画面離脱時の保存と直近操作が失われる範囲を明示する。idle待ちだけには依存しない。
- 形勢Workerへの転送量・頻度とキャッシュ保存を測定する。必要なら初期状態を一度送り、以降はrevision付き差分コマンドを送る。古い計算結果は破棄する。
- サーバーではRedis読込・盤面実行・保存・送信を別々に測る。現在は統計カウンター更新もview配信より前にawaitされるため、計測上問題があれば確実な再試行付きで配信後へ移す。盤面の永続化・競合検証は配信前に完了させる。

## 5. 秘匿情報とルールの条件

`docs/game-rules.md` を優先し、`applyCommand` と効果解決順を演出都合で変更しない。

- おにごっこの判定、回避時の攻撃無効・行動済み、攻撃時効果、リンネ等の反応順を守る。
- あみの・うぃまる・ぶらんちゃん等の反応が未解決なら、ダメージ・登場・PP支払いなどを確定表示しない。
- ダイス結果・ドロー結果・相手の非公開カードをクライアントで予測して確定しない。
- 表示イベントには対戦ID・revision・操作IDを関連付ける。自分の操作に対する受信で同じ移動や攻撃を二度再生しない。
- 再接続時は新しい正規盤面へ同期し、古い仮表示・タイマー・キュー・入力ロックを片付ける。拒否されたコマンドを自動で再送しない。

**偽ラグの一律削除は初回改修に含めない。** 現行のランダムな待機だけでタイミングからの推測を完全に防げるとも扱わない。

反応の有無による時間差をさらに減らす場合は、公開情報だけで決める共通の反応受付窓をサーバー側に設け、反応のない場合も同じ窓を通す案を別途評価する。この方式には反応可能な操作すべてに最低待ち時間が加わる。長く考えた場合の漏れも含めて評価し、待機中の構え演出で操作が受理済みだと伝える。窓の長さや自動パスはプレイ感とルール運用の判断が必要で、今回の速度改善の前提にはしない。

## 6. 実装順と評価

1. **測定**：カードプレイ・攻撃について、入力、最初の視覚反応、処理開始/終了、WS送信/受信、正規盤面受理、着地/着弾、操作解禁を記録する。反応カード・偽ラグ・通信待ちを別タグにする。
2. **処理と演出の分離**：受付時に実行・送信し、仮表示と確定結果を接続する。装飾と入力ロックを分ける。通常のプレイ・攻撃を最初の対象とする。
3. **準備処理**：対戦資産の段階的先読みと画像サイズ統一、Workerの事前起動を追加する。
4. **計測で残った負荷への対応**：Context・保存・Worker転送・サーバーを必要な順に改善する。
5. **反応待ちの改善**：秘匿性とプレイ感を評価してから、偽ラグと反応受付窓の方針を決める。

本番ビルドで、スマホ・PC、画像キャッシュ有無、CPU対戦・オンライン対戦を比較する。オンラインは実際の回線と遅延を加えた条件を分ける。平均だけでなくp50/p95、長いメインスレッド処理、フレーム落ち、画像取得・デコード、メモリも確認する。既存の `docs/performance/game-performance.md` は主に準備画面の記録なので、対戦操作の基準値には使わない。

実装時の確認対象：通常プレイ、連打、空きスロットへのドロップ、早食い・突撃、防衛・かくれんぼ・挑発、おにごっこ成功/失敗、反応あり/なし・反応拒否、対象選択、破壊時連鎖、勝敗、再接続、古いrevision拒否、CPU、undo、リプレイ、演出短縮、タブ復帰。ゲームコマンドの結果と順序を既存と比較し、演出終了が来ない場合にも操作ロックが解除・復旧されることを確認する。

この設計変更自体ではテストは実行していない。実装時はゲーム状態と非同期の表示をまたぐ変更になるため、coreの既存テストと、操作・拒否・再接続のUIテストを行う。
