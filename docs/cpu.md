2026-10-22にリポジトリ内の実装と照合した。数値は組み込みCPUの現行値。外部CPUサーバーが配るモデルの重みや、本番の環境変数は今回確認していない。ルールの正は [ルール・裁定集](game-rules.md)。ここに書く点数はCPUの判断用であり、カードの効果・裁定ではない。

主な参照先：[基本の重み](#基本の盤面評価と正確な重み)、[カード別の補正](#お菓子ごとの手札価値-sweetvalue)、[探索設定](#探索の設定と選び方)、[学習モデルと全入力](#学習モデルの構造入力重み)、[学習・比較](#学習と比較)。

重みの調整は「基本の盤面評価」と該当する補正、探索の変更は「探索の設定」、モデルの変更は「学習モデル」と「学習と比較」を読む。末尾の過去の実験記録は比較方法や既試行の確認が必要なときだけ参照する。数値の正本はリンク先の実装で、全係数配列を通常のCPU改修時に読む必要はない。

## 判断の流れと難易度

全難易度に共通して、[moves.ts](../packages/game-core/src/ai/moves.ts) が候補コマンドを実際のエンジンに適用し、受理された手と適用後の状態を列挙する。カード固有の効果もこのエンジンで処理する。

[hidden.ts](../packages/game-core/src/ai/hidden.ts) は、自分の山札順と相手の未公開手札・同種の山札を混ぜ、乱数の種も置き換える。デッキ内容は既知として扱うが、実際の順番・未公開手札・未来の出目は使わない。[index.ts](../packages/game-core/src/ai/index.ts) が実際の状態で選んだコマンドを再検証する。

| 難易度 | 判断方法 |
| --- | --- |
| よわい | 即勝利の手を優先。明らかな無駄と敗北する手を避け、残りからランダム。終了できる場合は、他の行動があっても1/8で終了する |
| ふつう | カード・効果・スキルごとの定石。使う価値のある高コストのカード、スキル、お菓子への攻撃、低体力の敵への攻撃の順。初手は幼女2枚を目安に引き、コスト4以上を交換する |
| つよい | 最大20局面の勝ち筋探索。その後は各手の適用結果を `evaluate` で採点。自分の対象選択等は追加で深さ3まで読む。反応スキルの判断は「ふつう」を使う |
| さいきょう | 最大4000局面の勝ち筋探索。その後は自分のターンと相手の返しをビーム探索。途中は `evaluatePlan`、ターン終了局面は学習済み評価。1コマンド実行するごとに再探索する |

「つよい」は最良の行動が現在の評価を **0.5より大きく**改善しなければターンを終える。相手の反応で次ターンのPP負債が増えた場合、増加1につき3を加点する。`createHard(weights)` の既定は勝ち筋探索なしで、登録済みの `hard` だけが20局面を指定する。「さいきょう」のフォールバックと学習用自己対戦も探索なしの `createHard` を使う。

実装：[easy.ts](../packages/game-core/src/ai/levels/easy.ts)、[normal.ts](../packages/game-core/src/ai/levels/normal.ts)、[hard.ts](../packages/game-core/src/ai/levels/hard.ts)、[master.ts](../packages/game-core/src/ai/levels/master.ts)。`createMaster()` 単体は学習評価を指定しない。アプリの登録済み `master` と有効な配信モデルを使う経路が `createValueEvaluator` を渡す。

## 基本の盤面評価と正確な重み

出典：[evaluate.ts](../packages/game-core/src/ai/evaluate.ts)、[planning.ts](../packages/game-core/src/ai/planning.ts)。

| 項目 | キー | つよい：`defaultWeights` | さいきょうの途中：`planWeights` |
| --- | --- | ---: | ---: |
| お菓子ポイント1 | points | 10 | 10 |
| 場の攻撃力1 | unitAttack | 4.6 | 4.2 |
| 場の体力1（負値は0） | unitHp | 3.14 | 2.5 |
| 防衛または挑発の幼女1体 | defender | 3.7 | 4 |
| 手札1枚 | hand | 2.15 | 2.15 |
| 最大PP1 | maxPp | 0.64 | 0.64 |
| 場の幼女1体への固定加点 | unit | 0 | 0 |
| お菓子ポイント5未満の不足1 | danger | 0 | 7 |
| 貫通の幼女1体 | pierce | 0 | 3 |
| 早食いまたは突撃の幼女1体 | quick | 0 | 0.2 |
| 通常スキルの残り使用回数1 | skill | 0 | 0.6 |

各側の基本点 `S` は次の式。`w` は上表の該当列、`I(条件)` は成立時1、それ以外0。

```text
S = points × w.points + hand枚数 × w.hand + maxPp × w.maxPp
    − max(0, 5 − points) × w.danger
    + 通常スキル残回数の合計 × w.skill + MP × 1.5
    + I(プレイヤーのshield) × w.points
    + 場の各幼女について以下の合計

幼女の点 = w.unit + attack × w.unitAttack + max(0, hp) × w.unitHp
          + I(shield) × w.unitHp
          − I(immobilized) × attack × w.unitAttack × 0.4
          + I(防衛 OR 挑発) × w.defender
          + I(貫通) × w.pierce
          + I(早食い OR 突撃) × w.quick

evaluate = S(自分) − S(相手)
```

防衛と挑発の両方、早食いと突撃の両方があっても、それぞれの加点は1回。PPは現在値でなく `maxPp` ヘルパーの値。勝利は `+1,000,000`、敗北は `−1,000,000`。`evaluate` 自体には引き分け専用の0点分岐はなく、通常式へ進む。`evaluatePlan` と学習評価には引き分け0点の分岐がある。

## さいきょうの途中評価に加わる補正

```text
evaluatePlan = evaluate(planWeights)
             + resources(自分) − resources(相手)
             + danger(相手) − danger(自分)
```

この `danger` は、重み表の `danger` と別の補正。相手から受ける概算打点を `damage`、自分のポイントを `points` とすると、`damage >= points` なら `90 + (damage − points) × 8`、それ以外は `max(0, damage − points + 3) × 4`。

概算打点 `pressure` は、お菓子へ攻撃できそうな場の攻撃力の合計。防衛があれば貫通以外の通常打点を0とし、行動不能・食べられない幼女などを除く。自分のターンは行動済み・登場直後の早食いなしも除く。`y_20` の追加2点を見積もり、相手にshieldがあれば正の打点の最小1回分を差し引く。これは近似であり、正確な攻撃・対象制約は探索中のエンジン適用で解決する。

### 手札・PP・山札

| 補正 | 正確な式・係数 |
| --- | --- |
| 次ターンに使えるPPの見積もり | `max(0, min(12, maxPp + 1) − nextPpDebt)` |
| 次ターンのコスト見積もり | `max(0, costOf − temporaryCost)` |
| 手札の利用係数 `ready` | 上記コストが見積もりPP以下なら0.28、超えるなら0.09 |
| 手札の幼女 | `(攻撃×4.2 + 非負体力×2.5 + I(onDestroyedあり)×3 + I(早食い)×3) × ready` |
| 手札のお菓子等 | `min(30, sweetValue) × ready`。公開済み `s_24` はさらに0.3 |
| 次ターンのPP負債 | `−nextPpDebt × 3` |
| 現在PP（手番側だけ） | `min(現在PP, 手札の現在コスト合計) × 0.9` |
| 残り山札 | 幼女山札・お菓子山札それぞれの手札評価の平均 × 0.25（空なら0） |

`resources` はこれらと次節のコンボ補正を合計する。手札枚数の基本点2.15に加えて、手札の中身も評価する。

### お菓子ごとの手札価値 `sweetValue`

以下は効果の近似価値。カード原文の代わりには使わない。IDの原典：[sweet.json](../src/data/sweet.json)。

```text
U(幼女) = 攻撃×4.2 + 非負体力×2.5
H(n) = min(n, max(0, 最大ポイント − 現在ポイント)) × 7
F = 場の幼女数が正ならその数、いなければ min(2, 手札の幼女数)
B(n) = Fが正なら n×6.7、いなければ0
K = 使用済みカードと評価対象カードに含まれるケーキの種類数

対象へのダメージ価値(n):
  効果無効またはshield持ち → 0
  体力 <= n → U(対象)
  それ以外 → min(n, 体力)×2.5
D(n) = 敵1体へのダメージ価値の最大（敵なしは0）
A(n) = 敵全体へのダメージ価値の合計
```

### コンボ・組み合わせ

`access(id)` は手札・場にあれば1、なければ該当山札内の割合×0.35。指定により場を除く場合もある。

- `y_15` と `y_16`：`7 × min(access(y_15, 場を除く), access(y_16))`。
- ケーキ・動物さんソーダ・フロートをそれぞれ評価：`min(3, 使用済み種類数) × Σaccess(未使用で手札・山札にある種類) × 2`。
- お菓子強化：動物さんソーダ以外の実お菓子について、`sweetBoost × min(35, max(手札の最大sweetValue×0.65, 山札の平均sweetValue×0.15))`。
- 敵とのリンク：味方幼女ごとに、`(リンク先の場の敵のU合計 − 自身のU) × 0.18`。

### 引く山札と探索の並べ替え

`drawValue` は、該当山札の手札評価の平均に以下を加える。空の山札は `−Infinity`。先頭カードは参照しない。

- 引く候補が `y_15` なら `7×access(y_16)`、`y_16` なら `7×access(y_15, 場を除く)` を平均前に加える。
- 幼女を引く：場＋手札の幼女が2未満なら8、そうでなく手札の幼女0枚なら3、それ以外0。
- お菓子を引く：手札の実お菓子0枚なら6、1枚なら2、それ以外0。
- 効果元 `y_6` から幼女なら4.2、`y_8` からお菓子なら5。
- 効果元 `y_27` から幼女で、`pending.task.ids`（未設定は空）の全カードが幼女なら1。
- 効果元 `s_18`：幼女なら10、お菓子なら回復余地ありで7、それ以外0。

`orderPlan` は `evaluatePlan` に、自分が選ぶ未解決効果がある場合8を加える。ただし `discard / trimHand / gift / diceDiscard` は除く。解決前の準備手順を探索に残すための加点で、ターン終了評価には使わない。

## 探索の設定と選び方

出典：[turn-search.ts](../packages/game-core/src/ai/turn-search.ts)。

| 設定 | 既定値 | 指定できる範囲 |
| --- | ---: | --- |
| maxNodes | 2400 | 100〜20000 |
| beamWidth | 4 | 1〜32 |
| maxDepth（対象選択も1コマンド） | 14 | 2〜32 |
| worlds（仮の手札・山札・乱数） | 3 | 1〜8 |
| candidates（準備探索から残す初手） | 4 | 1〜12 |
| policyOrder（実験用） | 0.5 | 上記の整数範囲処理なし |
| policyRoot（実験用） | 0 | 上記の整数範囲処理なし |

既定の `master` は `policy` を渡さないため、policyの係数は効かない。

1. 準備探索に `min(floor(maxNodes/4), 180)` 局面を割き、有望な初手を最大 `candidates` 個取り出す。
2. フォールバックの初手とターン終了も加える。重複は除くので、初手数は常に4とは限らない。policyを指定した実験では、その最良手も加える。
3. 各初手・各worldへ残予算を均等配分。world数は予算に応じて減る。worldあたりの予算は `max(1, floor((maxNodes−準備探索ノード数)/(初手数×world数)))`。
4. その40%（切り捨て、最低1）を自分の手順に使う。残りを3で割った予算（切り捨て、最低1）で、自分の上位3手順それぞれへの相手の返しを探す。相手のbeam幅は `max(1, floor(beamWidth/2))`。
5. 各段階で高評価の枝をbeam幅まで残す。ただし初段は予算内で各初手の2段目を読む余地を残す。同じ初手につき完成手順を最大3本保持する。
6. 探索された相手の返しの最小評価をその手順の点数とし、自分はその点数が最大の手順を選ぶ。
7. world間では `mean − (mean−min)×0.25`、つまり **平均×0.75＋最低×0.25** を採用する。

policyを指定した実験では、途中の並べ替えに `(手のlogit−候補の最大logit)×policyOrder×68`、最終評価に `policyRoot×68×初手のlogit` を加える。この68は探索側の定数で、組み込みモデルのscale=68.1とは別。

`maxNodes` はbeam展開用の予算であり、すべてのエンジン適用回数や実行時間の厳密な上限ではない。打ち切った手順は最大64ステップで選択・有益な攻撃・ターン終了まで進める。攻撃は途中評価が0.5より大きく改善するときだけ行う。相手ターンへ到達できなかった異常に長い効果列は、途中評価から30を引く。相手が選ぶ効果は相手視点の近似採点で1手に絞るため、すべての応手を調べるminimaxではない。

勝ち筋探索は別予算：[lethal.ts](../packages/game-core/src/ai/lethal.ts)。深さ優先で重複局面を省き、終了手を除いて探索する。ドロー・乱数を通る手順は、さらに乱数・自分の山札順を変えた **8パターン** で再生する。

2026-10-24、LLMが考えた準備手順とゲームエンジンの探索、またはさいきょうCPUを組み合わせ、当時公開されていたメロン初級・中級7問すべてでseed 1・2・3の同一ターン勝利を確認した。解答コマンド列と再生テストは [lethal-puzzle-solutions.json](../packages/game-core/tests/fixtures/lethal-puzzle-solutions.json) と [lethal-puzzle-solutions.test.mjs](../packages/game-core/tests/lethal-puzzle-solutions.test.mjs)。初級①・②は初期局面から探索し、それぞれ9354・6670局面。中級①は「かんらんを出す」から12局面、中級③は「レンテを出す」から13局面、中級④はPPスキル→さら→猫2枚を選択→なかよしから17局面、中級⑤は「しゅおを出す」から7962局面で勝ち筋を発見した。中級②はさいきょうCPUが毎手再探索した。局面数は準備手順の後の探索量であり、LLM候補の生成費用を含まない。3つのseedでの再生確認であって、すべての乱数・相手の選択に対する完全証明ではない。

勝ち筋探索の並べ替えは、各手を適用した状態について次の `distance` が小さい順。同点なら、決着した手→お菓子への攻撃→プレイ・選択→幼女への攻撃→スキル→その他の順で読む。

```text
防衛1体の障害点 G = 30 + 非負体力×3 + I(shield)×5
obstruction = 敵の防衛のG合計
distance = 敵ポイント×12 + obstruction + I(敵shield)×10
           − 攻撃準備の点数 − 自分の現在PP×0.1
```

自分のダメージ対象選択が未解決なら、選べる防衛のうち最も大きい除去見込み点を `obstruction` から引く。見込み点は、効果無効またはダメージ0以下なら0、shieldなら5、倒せるならG、倒せなければダメージ×3。ダメージは `amount×multiplier`（未設定はそれぞれ0・1）。

攻撃準備の点数は、未行動・正の攻撃力・immobileなしの味方ごとに加算する。登場ターンでないか早食いなら `ready`、`ready` または突撃なら `canTrade` とする。`ready` かつnoEatなしなら攻撃力×6、`canTrade` かつobstruction>0なら攻撃力×2、`y_20` で `ready` または（`canTrade` かつ敵幼女あり）なら12。勝利した状態のdistanceは−1e9、その他の決着は+1e9。

`win` はその有限の検証に通った意味で、あらゆる未公開手札・出目に対する数学的な保証ではない。`none` は対応する分岐を予算内で調べ切って検証を通る手順なし、`unknown` は局面数の上限に到達した意味。相手の任意選択が必要な分岐は打ち切り、相手の10・5ポイント時のお菓子強制ドローだけは進める。

| 30 / 31 | sweetBoost / 2、お昼寝場所枚数 / 20 |
| 32 / 33 | pressure / 12、pressure >= 敵points のフラグ |
| 34 | 未解決効果の選択者が自分のフラグ |
| 35 | 公開済み手札枚数 / 5 |
| 36 | 手札の現在コスト合計 / 30 |
| 37 | 予算内の手札枚数 / 5。予算は手番なら現在PP、それ以外 min(12, maxPp+1) |
| 38 | 自分視点のevaluatePlan / 100 |

「公開36」は実装上の区分名。index 12の相手の手札内訳などは実情報ではなく `determinize` した仮の値を使う。特徴23は能力フラグによる近似で、正確な合法攻撃判定ではない。正規化の除数は上限を意味せず、値が1を超える場合がある。

```text
F(x) = Σ linear[i]×x[i]
       + Σ out[j]×tanh(bias[j] + Σ first[i×hidden+j]×x[i])
z = F(自分39＋相手公開36) − F(相手39＋自分公開36)
学習評価 = z×scale + (自分MP−相手MP)×1.5
```

勝利・敗北は±1,000,000、引き分けは0へ先に分岐する。`z` は勝敗を学習したlogitで、確率表示にするなら `sigmoid(z)`。探索は確率そのものではなく上記の点数を使う。MPの1.5は学習外の加点だが、特徴38の手書き評価にもMPの点数が含まれる。

カードIDをモデルへ直接入力していない一方、特徴38にはカード固有の手書き評価が間接的に入る。能力値合計だけを見るモデルでも、カードごとの方策を直接学ぶモデルでもない。tanhと両側の差分を含むため「防衛は常に何点」のように学習重みを単独の固定加点へ置き換えられない。

## 学習と比較

[value-train.ts](../packages/game-core/src/ai/value-train.ts) の現行既定値：

| 項目 | 値 |
| --- | --- |
| 自己対戦の方策 | 探索なしのcreateHard＋25%でランダム合法手 |
| 通常の自己対戦デッキ | ランダムないちごデッキ |
| 保存局面 | ターン開始時。CLI・サーバーの標準採取率0.5 |
| CLI・サーバーの標準自己対戦数 | 40000試合 |
| 学習・検証分割 | match ID % 10 == 0 を検証へ。同一試合を分離しない |
| 教師 | 勝敗。実験用に探索ラベル・確率ラベルも受け取れる |
| hidden / epochs / batch | 32 / 4 / 128 |
| 損失 | logitに対する二値交差エントロピー |
| 最適化 | Adam形式、β1=0.9、β2=0.999、ε=1e−8 |
| 学習率 | `0.002×0.5×(1+cos(π×(epoch−1)/epochs))`、epochは1始まり |
| 正則化 | 勾配へ `1e−5×重み` を加える（biasも含む） |
| 採用epoch | 検証loss最小 |
| 保存 | 係数は小数4桁、scaleは小数2桁に丸める |

scaleは、検証局面の手書き評価の標準偏差をモデルlogitの標準偏差で割る。サーバーの人との対戦局面の重みは既定3、20件の新規記録を目安に再学習するが、環境変数で変わる。配信・同意・記録検証の仕様は [CPUサーバー](../services/cpu-server/README.md) を参照する。

```sh
pnpm run cpu:arena -- [試合数] [レベル…]
pnpm run cpu:train -- [世代数=30] [候補数=8] [1候補あたりの組数=100]
pnpm run cpu:value -- collect [試合数=40000] [保存率=0.5]
pnpm run cpu:value -- train [hidden=32] [epochs=4]
pnpm run cpu:value -- adopt
pnpm run cpu:policy -- [試合数=20000] [保存率=0.2] [hidden=48] [epochs=4]
pnpm run cpu:compare -- <名前> [--model f.json] [--policy f.json] [--search '{…}'] [--decks all|strawberry|records.jsonl]
```

`cpu:train` は基本評価の重み候補を対戦で選ぶ処理、`cpu:value` は盤面評価モデルの学習、`cpu:policy` は行動の価値の学習。`adopt` は生成モデルを組み込みファイルへ写すため、比較してから実行する。

[compare.ts](../packages/game-core/src/ai/compare.ts) の比較既定は、互角の勝率0.5に対して強いとする勝率0.55、α=β=0.05、最大600の決着試合によるSPRT。引き分け・勝者なしはwins/matchesに含めない。上限で未確定なら不採用とする。勝敗の予測精度だけで強くなったと判断しない。

## 過去の実験記録と制約

以下はgame-coreのREADMEから集約した過去の記録であり、2026-10-22に再計測した値ではない。カード・ルール・実行環境が変わった現行CPUの勝率や時間を保証しない。

| 対戦 | 試合数 | 過去の勝率 | 過去の平均思考時間 |
| --- | ---: | --- | --- |
| ふつう vs よわい | 2000 | 90.5%（記録上の95%区間89.2–91.7） | 0.1ms |
| つよい vs ふつう | 1000 | 81.8%（79.5–84.1） | 2ms |
| つよい vs 勝ち筋探索なし | 1000 | 57.9%（記録上56.3–59.5。区間の算出条件は未再確認） | — |
| さいきょう vs つよい | 120 | 83.3%（76.9–89.8） | 109ms |
| 学習評価 vs 手書き評価のさいきょう | 400 | 63.0%（59.1–66.9） | 同程度との記録 |

- 基本重みの1回目の育成は初期値比53.4%。2回目は51.6%で採用しなかった。
- カード名の直接入力は予測精度を改善したが指し手を悪化させた。学習評価をターン途中にも使った実験は「つよい」への勝率20%との記録。
- 探索ラベル、人との33試合の混合、相手の返しの拡大などは当時の比較では改善を確認できなかった。あらゆる学習方法で効果がないという意味ではない。
- policyモデルの実験は予測精度71.6%、既存さいきょうとの200試合で51.5%、設定を変えて46.0%・51.5%。時間約1.3倍で、標準のさいきょうには未採用。
- 準備・温存の手が途中の採点で落ちることが弱点という仮説がある。探索途中の手書き評価、カード固有の表現、候補の残し方を分けて比較する。

CPUを変更するときは、上記の重み・入力・探索設定の該当箇所を更新する。ルール再実装を別言語へ複製せず、同じゲームエンジンでデータ作成と対戦評価を行う。
