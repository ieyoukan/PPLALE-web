# 対戦履歴と保存済みリプレイ

## 保存するもの

対人戦（ルーム・フリー）の開始状態、受理した全操作、操作後の完全な `GameState`、両者の使用デッキ、カード定義・画像、実行エンジンのバージョン、表示用の攻撃・残HP・コスト・PP上限を保存する。ダイス、選択肢、乱数状態、非公開領域、ログも含む。現在のルールで操作を再実行せず、保存した各フレームを表示するので、後のルール・画像変更で当時の対戦が変化しない。画面のアニメーションは再生用のもの。操作と操作の間の待ち時間・通信時間は再現対象外。

一覧・お気に入り・詳細・自分と相手のデッキ確認・再生/停止・一手/ターン移動・速度/視点変更・JSONダウンロードに対応。履歴の件数・保存期間の自動削除はない。部屋の再利用や再戦は別の試合UUIDで管理する。

## Redisを維持し、履歴をPostgreSQLに保存

- 旧Podも新Podも同じRedisのルーム・フリーマッチ待機列を読む。ルームをSQLite等の別ストアへ移さない。
- Redis LuaのルームCAS（または待機列と新ルームの同時作成）と**同じ原子的操作**で、保存待ちのスナップショットをRedis Streamに追加する。CAS失敗は履歴を作らない。
- StreamにTTLや長さ上限は設定しない。PostgreSQLのトランザクションで記録した後だけ削除する。保存失敗時は成功応答を返さず、Pod再起動・別Pod・定期回収で再試行する。
- 同時回収や応答の喪失で重複して届いても、Stream IDとDBトランザクションによって同じフレームを二重に追加しない。未保存状態を通常の操作成功として通知しない。
- 操作を受理したPodがそのエンジンで算出した表示情報とカタログを添付する。履歴サービスのバージョンで計算し直さない。
- PostgreSQLには部屋の復旧用コピーも保存する。Redis AOFの直近1秒が巻き戻ったときは、確認済みの新しい状態で復旧する。部屋のTTLが過ぎても履歴は残る。
- 部屋・デッキの秘密情報や所有者キーをRoomViewやダウンロードするリプレイに含めない。

初回のローリング更新中は、履歴に非対応の旧Podが操作を受理し得る。RedisのPod生存情報と記録能力の通知を照合し、混在中に開始した対戦は `complete: false` とする。初回導入より前から進行中の対戦や操作の欠けた記録を「完全なリプレイ」と表示しない。全Podが対応した後に開始した対戦が完全保存の対象。既存ルームを削除したり、更新のためにサービスを停止したりしない。

## PostgreSQLとバックアップ

SQLiteは追加DBの運用を避ける当初案だったが、並列アクセス、ローリング更新、独立したバックアップ運用を優先し、未デプロイのSQLite実装を廃止した。外部の従量課金DBは追加せず、自宅k3sに専用PostgreSQLを置く。CMS等の他アプリのDB・認証情報とは共有しない。

本番はprimaryと同期standbyの2台（別Kubernetesノード、各10Giの保持PVC）。`synchronous_commit=remote_apply` のCOMMITを待ち、standbyに適用される前に保存成功としない。standby切断時は書き込みが待機する。COMMITへのタイムアウトキャンセルによってprimaryだけの保存を成功扱いしないため、COMMITのstatement_timeoutは無効化する。RPCがタイムアウトした場合も保存待ちStreamを保持し、再試行時は新しいWAL書き込みでそれ以前の記録の同期を確認する。

日次の `pg_dump -Fc` は**独立CronJob**で動かす。HTTPのイベントループでDB全体をコピー・検査しない。PostgreSQLのMVCCスナップショットなので、通常の対戦書き込みをバックアップの完了までロックしない。NAS (`nfs-client`) の保持PVCへチェックサム付きで保存し、成功したスナップショットを14世代残す。失敗したJobは失敗として残り、既存バックアップを消さない。対戦履歴そのものの削除とは別。

フレームはgzipとSHA-256の連鎖、カタログ・画像・メタデータもハッシュを保存する。破損・欠落は読み出しを失敗させ、壊れたリプレイを返さない。

### 初期設定

`history.existingSecret` は `password` キーのあるKubernetes Secretを参照する。**Helm/Argoの描画ごとにパスワードを生成しない**。運用側で作成・保持し、Gitに平文を置かない。初期化後にSecretの値だけ変更してもPostgreSQLのパスワードは変わらない。変更時はDB側のロール変更と合わせる。

DBポートと履歴RPCはClusterIP限定、NetworkPolicyでアプリ内の必要なPodだけを許可。standbyの必要ノード分離は必須であり、配置先が不足しているときに1台保存へ黙って縮退しない。

### 復元

本番の既存DBへ直接上書きせず、隔離した**空のDB**へ復元し、完全性を確認してから接続先を切り替える。

1. NASから `.dump` と `.sha256` を取り出し、`sha256sum -c` を実行する（元のパスを必要に応じて合わせる）。
2. PostgreSQL 18以降の `pg_restore --exit-on-error --single-transaction --no-owner --dbname=<隔離DB> <file.dump>` を実行する。`--clean` は付けない。既存のテーブルがある場合はエラーで中止する。
3. ルームサーバーのコンテナで、隔離DBの `HISTORY_DATABASE_URL` を指定して `node scripts/verify-history.ts` を実行し、全フレーム、メタデータ、カタログ、画像のハッシュと参照を検査する。
4. 同期standbyを再構築し、同期状態を確認してからルームサーバーの接続先を切り替える。Redisの復旧用コピーと合わせて未処理Streamを回収する。

primary故障時のstandby昇格は自動ではない。元primaryを隔離して二重起動を防ぎ、standbyを昇格し、新しい同期standbyを用意するまでは保存を成功扱いしない。standbyのスロット保持WAL上限は2GB。長期停止で上限を超えた場合は、既存コピーを保全してbase backupから再構築する。

複数のKubernetesノード/PVCが、物理的にも独立した機器とは限らない。既存 `proxmox-data` の配置はインフラの責任範囲。NASを含む全コピーの同時破壊、認証情報の喪失、空き容量不足、長期間放置されたバックアップ失敗まで「絶対に失わない」と保証するものではない。保存容量の定期確認、Job失敗の監視、隔離DBへの定期復元確認が必要。新しいクラウド課金はないが、既存機材のストレージ・CPU・電力は使用する。

## 所有者と認証変更

ゲストはブラウザに保存した256ビットの秘密キーを使用し、サーバーにはSHA-256だけを保存する。ログイン時はFirebase ID tokenの署名、発行者、対象プロジェクト、有効期限を検証する。ユーザーIDの自己申告は使わない。ログイン中に開始した試合はアカウントだけに所属する。

ログイン時にその時点までの未所属ゲスト履歴をアカウントへ移し、お気に入りも引き継ぐ。他のアカウントに移った過去の履歴は再取得できない。ログアウト後に新しく始めたゲスト対戦は、そのゲストに所属する。ゲストキーを失うと未引き継ぎ履歴は復旧できないため、画面にログインによる引き継ぎを用意する。

一覧とリプレイは認証ユーザーIDをキーとするReactの子ツリーで保持する。別タブのログアウト/ユーザー切替をFirebase SDKが通知すると、一覧、開いた詳細、再生状態、カードモーダル、過去の読み込み結果をまとめて破棄し、新しい認証情報で取得する。旧リクエストが遅れて完了しても新しいツリーへ状態を渡さない。

## 確認

- 実Redis + PostgreSQLのCAS、競合、旧新Pod共有、未保存Streamの回収、応答済みデータからのRedis巻き戻り復旧。
- 180操作の全状態をエンジン結果と照合、SIGKILL後の再開、フリー対戦、切断決着、期限切れ、再戦、ページング、データ破損。
- 同期standbyの適用を停止したまま保存成功が返らないこと、再開後に2台で一致すること。
- 遅い読み取りスナップショット中も対戦操作・ヘルスチェックが継続すること。
- Playwrightで1280/375/320pxのUI、固定v1 fixtureの再生/出力、両デッキ確認、実FirebaseのIndexedDB監視による別タブのログアウト/切替、遅延レスポンス後も旧データが戻らないこと。
