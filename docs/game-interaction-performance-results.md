# 対プレイヤー戦の応答改善・計測記録

2026-10-18。作業ツリーの変更。Web・ルームサーバーとも、この作業から本番へのデプロイは行っていない。

## 変更

- 自分の操作は演出開始時にWebSocketへ送信する。攻撃・手札反応を隠す待機・カード紹介のタイマーが終わってから送る直列処理をやめた。受信した盤面の表示は、必要な演出の到達時点まで待つ。
- ダメージ・登場・PP等の確定結果は引き続きサーバーから受け取る。手札反応の存在を隠す偽ラグは残すが、通信と重ねる。
- オンラインの演出時間は一度短縮した（攻撃720→300ms、カード紹介2400→900ms等）が、観戦で速すぎて追えないため、CPU戦と同じ長さに戻した。待ち時間は通信を演出と重ねることで減らし、演出そのものは縮めない。JSの待機とCSSの時間は共通の設定から渡し、移動を減らす設定もJS側へ反映する。
- 送信した手札はすぐ光る。同期的な入力ガードで連打を防ぎ、送信失敗時は仮の演出を終了する。
- 初期ドローは相手のカード移動と並行して受信・表示する。入力ガードも相手の演出終了を待たず解除し、双方が独立して引けるルールを保つ。
- WebSocketの応答が12秒来なければ再接続する。操作は自動再送せず正規盤面を再取得する。切断中はゲーム操作を止める。
- デッキ選択・マッチング中に対戦画面をprefetchし、自分が選んだデッキの盤面・手札用画像を最大2件ずつ取得・デコードする。取得失敗を開始条件にしない。画像の候補生成は `getImageProps` を使い、実表示と同じ `sizes` を共有する。飛行・ドラッグ表示も手札用の画像候補を使う。
- Redisでプレイヤー2席と観戦者の接続数を取る処理を一つのLua呼び出しにまとめた（従来は各席で期限切れ削除と件数取得、計6コマンド）。
- 対戦の統計カウンター更新を盤面配信・応答の後に行う。カウンター障害で、確定済みの操作を失敗と返さない。統計はbest effortで、失敗はサーバーログに記録する。盤面・履歴の永続化待ちは維持する。

## 本番への読み取り専用の確認

稼働中のルームにコマンドを送ったり、設定を変えたりはしていない。

| 対象 | サンプル | p50 | p95 | 最大 |
| --- | ---: | ---: | ---: | ---: |
| サーバーPod→RedisのPING | 40 | 0.165ms | 0.414ms | 0.828ms |
| サーバーPod→履歴RPCのPING | 20 | 5.482ms | 18.241ms | 111.090ms |

公開 `/stats` のHTTPS応答は1回で140.9ms。Podは2台、Redisを利用していた。このHTTPS測定はTLS・経路を含み、対戦のWebSocket往復時間を測った値ではない。PodのCPUは当時7〜8m、メモリ44〜47MiBだった。いずれも短時間の観測であり、混雑時間帯の保証にはならない。

履歴RPCのPINGは記録のCOMMIT時間を測っていない。現行 `durableBackend` は読込・更新の前後で履歴outboxの反映を待つため、実際の操作ではこの時間が加わり得る。保存保証を落とす変更はしていない。新しい段階別計測の `read` / `store` には、この履歴待ちも含まれる。

## ローカルの比較

Node v22.23.2。実際のローカルWebSocketでプレイ・攻撃・選択・ターン終了等を160操作ずつ実行。ブラウザの描画・本番回線・PostgreSQL履歴保存は含まない。各実行のシャッフルとコマンド内訳は異なる。ホスト上では他の開発作業も動いているため、数msの差を厳密な改善率として扱わない。

| バックエンド条件 | 改善前 p50 / p95 | 改善後 p50 / p95 |
| --- | --- | --- |
| メモリ・追加遅延なし | 0.84 / 1.36ms | 0.83 / 2.18ms |

## 今後の計測方法

本番反映後の `/stats` は、そのPodの直近256成功コマンドについて `latency.milliseconds` を返す。

| 項目 | 範囲 |
| --- | --- |
| `queue` | WebSocket受信から、そのソケットの処理開始まで |
| `read` | 盤面取得。履歴の復元・反映待ちを含む |
| `apply` | 検証・ルール処理 |
| `store` | 盤面保存。履歴の永続化待ちを含む |
| `presence` | 接続人数取得 |
| `deliver` | ローカルの各席用盤面生成・JSON化・ソケットへの送信登録 |
| `publish` | 他Podへの更新通知の送信 |
| `total` | 受信から応答の送信登録まで |

各項目はp50/p95/最大。Pod・再起動ごとに別の集計で、集計したp95同士を足して合計時間にしない。接続先Podまでの回線時間や、他Podが実際に配信するまでの時間は含まない。名前・カード・ルームIDは計測に保存しない。

ブラウザでは `performance.getEntriesByName('pplale:room-command-roundtrip')` で直近の送信→結果受信時間を確認できる。128件で測定エントリをリセットする。拒否された要求も含むが、タイムアウトは含まない。

再測定：

```sh
node services/room-server/scripts/measure-latency.ts /tmp/room-latency.json
BENCH_COUNT_DELAY_MS=25 node services/room-server/scripts/measure-latency.ts /tmp/room-latency-slow-stats.json
REDIS_URL=redis://127.0.0.1:6379 node services/room-server/scripts/measure-latency.ts /tmp/room-latency-redis.json
```

計測スクリプトは専用ルームとRedisの専用prefixを作る。Redisへの各呼び出しは重なり得るため、スクリプトの `backendMs` を足して往復時間と比較しない。初回の変更後JSONでは、非同期にした `backendMs.count` の操作別の帰属が正しくないため、この欄を評価に使わない。往復時間の計測には影響しない。スクリプトの計測先参照は修正済み。変更後はサーバー自身の `serverLatency` も取得できる（開始前の操作も含むため、160操作の集計とは件数が異なる）。

## 検証

- TypeScriptの型チェック。
- 変更箇所のESLint。
- 既存ルームサーバーテスト、計測の件数上限・接続数の期限切れ・統計待ちの追加テスト。
- 実Redisで接続数集計、2台構成での対戦・再接続、フリーマッチ。
- ブラウザで、攻撃の着弾前に送信済みであること、連打の抑止、結果を早く受信しても着弾前にポイントが変わらないこと、偽ラグ中にも送信すること、拒否時の復旧、応答が途切れた後に再送せず復旧することを確認済み。初期ドローの並行動作を含め、`e2e/room-latency.spec.mjs` に回帰ケースを残す。
- 上記5ケースと既存 `e2e/room-match.spec.mjs` の通常対戦・観戦2ケース、計7件が成功。実際の2人対戦は専用メモリサーバーで実行した。headlessの3D描画起動待ちを避けるため、サイコロは既存の代替表示を使用した。

ブラウザ検証は開発ビルドであり、本番の描画速度の測定ではない。キャッシュ・端末・回線を固定した本番操作のp95は、反映後に追加計測する必要がある。
